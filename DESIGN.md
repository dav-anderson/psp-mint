# psp-mint: design notes

How psp-mint is built, and why. The README has the build, the settings, the commands, the AIR calls and the local HTTP API; REGTEST.md has the regtest setup; this file has the reasoning. The sections were moved here from the README as they were, except where noted in [CHANGELOG.md](CHANGELOG.md).

## The scanner interface (silent payments deferred to the AIR)

The scan finds payments with `listsinceblock` from a checkpoint (`scan_checkpoint.json` in the network's data folder, the `lastblock` of the last successful scan), plus every payment already on record that is not settled yet, looked at again each scan. *Why:* the old scan read a fixed number of recent wallet transactions and could miss payments in a burst; `listsinceblock` sees every one since the checkpoint, and a reorg is handled because Bitcoin Core reports from the fork point.

Silent payments are not supported and are deferred to the AIR. To let them plug in later without touching settlement, the scanner exposes one narrow interface (`src/scan.rs`):

- `trait Node { fn call(&self, method: &str, params: Value) -> Result<Value, RpcError>; }`: the only way the scanner talks to a node. `Rpc` implements it; tests use a fake.
- `fn since(node: &dyn Node, checkpoint: Option<&Checkpoint>, target_confirmations: u32, pending: &[String]) -> Result<Since, RpcError>`: every payment since the checkpoint, plus the pending txids.
- `struct Since { received: Vec<Received>, next: Checkpoint }`: what was found, and the checkpoint to save once it has been processed.
- `struct Received { txid: String, confirmations: u32, value_sats: u64, payload: Option<Vec<u8>> }`: one payment to the PSP wallet, with the payload of its data output if any.
- `Checkpoint::load` / `save` in the data folder.

Settlement reads only `Received` values. A silent-payments scanner (which must find outputs by scanning every transaction with the PSP's scan key, not by wallet address) would be another source of `Received` values with its own checkpoint, and settlement would not change.

## Key rotation

psp-mint rotates its keys with the same scheme as fsp-mint (see [fsp-mint DESIGN.md](../fsp-mint/DESIGN.md), "Key rotation", for the full how and why): `rotation.activation_hours` (`PSP_ROTATION_ACTIVATION_HOURS`, default 8760) after the first issue, then every `rotation.period_hours` (`PSP_ROTATION_PERIOD_HOURS`, default **87600**, 10 years, because PSP is held as savings). Both are whole hours. **Either one set to 0 turns rotation off.** Restart-only settings (see "Restarting"). **Minimum period, a hard limit:** with rotation on, `psp-mint` refuses to start if the period is under 720 hours (30 days), whether it comes from `psp-mint.toml` or `PSP_ROTATION_PERIOD_HOURS`: "the PSP rotation period must be at least 720 hours (30 days, the claim window), so that the keyset a payer claims with outlives the claim window". The reason: a claim must name the **current** keyset (see "Purchase claims" below), and a payer has the whole 30-day window, counted from when the owed record lands, to claim. A payer who reads the record just after a rotation names the new set; one who reads it just before names a set that must still be current for as long as the window runs, or a rotation inside the window would make every claim in it fail with `keyset_not_current`. The floor is tied to `sp_wire::psp::CLAIM_WINDOW_SECS` in code (`config::MIN_PSP_ROTATION_PERIOD_HOURS`, 720). PSP only: fsp-mint and esp-mint have no policy minimum (their period is whole hours, at least 1, and in them only `activation_hours = 0` turns rotation off).

- **Two key sets, two spent lists.** Each key set (generation) is its own mint-core mint with its own sled store. Generation 0 is `mint_keys.json` and `db/`; generation N lives in `gen-N/`. The mint always runs through a `Rotor` and one shared set of settlement records, whether rotation is on or off: with rotation off there is one key set, generation 0, and nothing ever retires it. At each rotation the oldest generation is deleted with its spent list; its issued/redeemed totals move to `retired.json` so `/audit` still adds up.
- **First issue.** `first_issue.json` is written once, at the first check that sees anything issued.
- **Keyset-addressed, as fsp-mint.** Every request names keysets: a melt gives `keysets` (one per input, in order) and a rollover gives `input_keysets` and `keyset` (the set to sign the outputs with: the live set the request names, current or previous; a set that is not live is refused `keyset_retired` or `unknown_keyset`, nothing burned, and a stored answer is still replayed). The rollover request hash covers the whole request, every keyset field included. A pending rollover holds its inputs (`holds` in `rollovers.json`, saved with the pending entry before burning): another rollover naming one is refused, and a melt naming one gets `400 note_held`, nothing burned. Only a request resumed after a retirement (a rollover or a spend whose hash is pending) skips a note of a set that is no longer live, and only a note it holds itself, and only if its burn is proven under that request's hash: by its `burned` flag, or by the retirement proof, taken when the set is deleted (each note an unfinished request holds is checked against the retiring spent list, and the spent ones are saved under the holding request's hash as `burn_proofs` in the same `retired.json` write as the retired ID, before deletion). Otherwise `400 burn_not_proven`. A proof serves the request it was taken for and no other: a new request naming a proven note meets the refusal it would meet anyway (`keyset_retired` or `unknown_keyset`). A proof is dropped when its request finishes (one left by a crash between the finish and the drop is harmless and is trimmed at the next retirement). `retired.json` from 0.6.1 (a flat `burn_proofs` list) and `rollovers.json` from 0.6.1 (no `out_holds`) are not read: `serve` refuses to start and names the file. The same holds for a `retired.json` whose totals are JSON numbers (0.6.2 and earlier) and for a mint's store with 8-byte totals (see "Amounts"). Each note is verified, and its spent list chosen, by the ID it names; a retired ID is refused with `keyset_retired`, any other non-live ID with `unknown_keyset`, a missing list with `missing_keyset`, all before anything is burned. One melt can mix both live sets. The check-state call (over AIR) looks in both lists. The keysets call lists each live keyset's keys by ID (current and previous); the keys call is the current set only.
- **Purchase claims.** A purchase claim (kind 15) names the keyset its outputs are blinded for, and **it must be the current one**: the mint signs only with the current set. A claim that names the previous set is refused `keyset_not_current`, a retired set `keyset_retired`, a set it never had `unknown_keyset`. These three refusals are **not counted** against `claim.max_attempts`: a rotation is not the payer's fault, and the wallet fetches the current keyset (kind 4) right before it claims and sends the claim again with it. The owed record carries no keysets (the payer fetches the current set), and the answer names the keyset that signed, so a wallet unblinds with that keyset's keys even if it receives the answer after a rotation. A note signed by the previous set expires at the next rotation, sooner than one signed by the current set. **New work is always signed with the current keyset**, including the finish of a claim that was accepted before a crash (`claim::finish`, `service::recover`): a rotation does not wait for a pending claim, and there is no deferral of a retirement. A claim accepted for set A, not signed, and recovered after the mint rotated to B is signed with B's keys and the answer names B; the outputs A had signed before the crash stay in A's issued total, and the blind-nonce check still sees them in A's spent list. The blind-nonce check runs against the signing set's logic only, so the same blind nonce could be used once in each of two generations; in psp-mint that is not value-inflating (each note is still paid for) and is listed in [ROADMAP.md](../sandbox-mint/ROADMAP.md). In esp-mint it was: two exchanges with the same service and outputs under different keysets have one burn memo, so one burn of the PSP notes could be signed once under each (esp-mint 0.8.2 refuses a blind nonce that either live set has signed, and a request that has not melted before never takes a burn under its memo for its own).
- **Retired keyset list (fixed cap, not a setting).** When a rotation deletes a key set, its 8-byte keyset ID is appended to `retired.json`, written and synced *before* anything is deleted (a crash in between leaves the set listed and still on disk; the next start deletes it without listing it twice). A request naming a listed ID gets `keyset_retired` (those notes expired); an ID that is neither live nor listed gets `unknown_keyset` (junk, or never this mint's). That lets the mint tell genuinely expired notes from junk, so a wallet can explain a loss. The list is a cache capped at 1 MB of 8-byte IDs, **131,072 entries**, a constant in code and the same in every mint (`RETIRED_KEYSETS_CAP`); when full, the oldest ID is dropped. That covers hourly rotation for about 15 years, and a yearly mint never comes close; dropping only turns a very old `keyset_retired` answer into `unknown_keyset`. It is deliberately not configurable, an exception to "nothing hard-coded": it is too cheap to be worth tuning. In the file each ID is 16 hex characters, so a full list is about 2.5 to 3.5 MB of JSON on disk (quotes, commas and indentation included). The same file carries `burn_proofs`, by request (see "Keyset-addressed").
- **Deletion is crash-safe.** The retiring set's spent list and keys are renamed into `retiring-gen-N/` (keys last) and that folder is removed; a crash leaves the folder and the next start removes it. Stored rollover answers for a retired set are pruned (their notes are dead); burn memos are kept, because esp-mint's exchange crash recovery matches on them.

- **The rotation call (over AIR).** Read-only, the same shape as fsp-mint's: active flag, `first_issue`, `activation`, `rotation_period_hours`, current and previous keyset (ID, epoch, `starts`, `current_until`, `retires`), `next_rotation`, and the mint's clock `now`. The wallet uses it to time its staggered swap. `config` prints the same schedule for the operator.
- **The rollover call (over AIR).** Swaps notes for new notes of exactly the same amounts on the set the request names, current or previous (inputs sign `transaction_sighash`; no split). Crash-safe: the request is recorded in `rollovers.json` before the burn, and a retry gets the stored answer, or is finished (already-burned inputs skipped, outputs re-signed). A request resumed after a rotation is finished too: inputs of a set that retired meanwhile were already burned (proved as above), and outputs whose named set retired are signed with the current set (the reply names the keyset). Before anything is burned a new request's outputs are checked as its notes are: no blind nonce twice in the request (`duplicate_blind_nonce`), none the signing set has already signed (`blind_nonce_used`), none held by another unfinished rollover or spend (`note_held`). A pending request holds its output blind nonces beside its notes (`out_holds` in `rollovers.json`, saved with the pending entry before the burn, dropped when it finishes), so a request that burns and then cannot be finished is not made by repeating an output. A resumed request is not checked again.
- **It is also the PSP swap for handing PSP from wallet to wallet** (a developer to its app's user; see the ecash-wallet README). It already fits: exact amounts, the same denominations, no fee, the usual 1 MiB size limit (`server.melt_max_request_bytes`), the cheap checks first (count, amounts, denominations, then keys, signatures and the spent list), and crash-safe by request hash. If any input is already spent the whole swap is refused (`400`) and nothing is burned. That check lives in this mint; mint-core's own `swap` does not make it, a known limit that only matters to code calling mint-core directly (see the top-level `~/sandbox-mint/README.md`). No new route and no fee setting were added: a per-byte fee would make it a different route, and the hand-over swap is meant to cost nothing.
- **Lost.** PSP left untouched for a full cycle (10 to 20 years) is lost.
- **Claims left a full cycle.** Signatures delivered for a keyset that has since retired cannot be used: the wallet reports the outputs as expired. With a 10-year period this needs a claim answer left unused for years (the claim window is 30 days, so the answer comes at the latest then).
- mint-core is unchanged: the generation is picked in psp-mint before mint-core's primitives are called.

## Fees and junk requests

Fees are charged on requests that carry value. A request that carries no value is refused before anything can be charged, so fees do not stop junk requests; the body ceiling and cheap checks first bound their cost. Per-DID and per-connection rate limits at the AIR layer are a possible further mitigation, not yet explored.

## Wire format and versions

The request and response bodies, the payload and its sealed form, the key-set ID, the request hashes and the error codes are defined in the `sp-wire` crate, not here. `psp-mint` re-exports them (`psp_mint::payload`, `psp_mint::rotation::RolloverRequest`, `psp_mint::server::KeysetsResponse`, and so on). The ESP and FSP mints and the wallet build against the same crate, so they cannot drift from this mint by a byte.

`GET /health` returns `wire_version`, the crate's `WIRE_VERSION`. **Changing any encoded byte or JSON field in `sp-wire` means bumping `WIRE_VERSION`**, and a wallet refuses a mint that reports another number. Golden-bytes and size tests in `sp-wire` fail if a byte moves. **Version 4** is the claim rework: the payload is the 33-byte claim key, kind 15 is the purchase claim, and the owed record is the kind 13 body. It is a clean break: a payload, an owed record or a claim of version 3 is not read.

### Burn memos

An exchange at the ESP mint burns PSP notes and then issues ESP. If the ESP mint stops after the burn, its retry has to know whether the notes it finds spent were burned by that exchange or by someone else, since a PSP note is a bearer note and its holder could spend it somewhere else. A spent flag cannot say, so the PSP keeps the memo each note was burned under.

- Every note's spend signature covers the memo, so the memo cannot be changed without the holder's signature. For an exchange the memo is `SHA-256("esp-mint/exchange/v1" || service || each output's amount and blind nonce)`, which is fixed by the exchange's service and outputs.
- `/melt` runs every check first, with nothing written: each input's keyset, the note's proof, its spend signature over the memo, no note twice, each note unspent in its generation, and the key of its amount. Only then does it write the memo to `melt_memos.json` (a JSON object from note nonce, in hex, to memo) for every input, sync the file, and burn. It does this with the mint lock and the memo lock held, so no other burn can come between the checks, the record and the burn. **A `400` from `/melt` means nothing was burned and nothing was recorded**, so a refused melt leaves no memo on its notes. After the checks, a failure can only be a fault of the store (the memo file, or the mint's database), and it is answered `500`. The record goes before the burn, not after, because a crash between the two must never leave notes spent with no memo: the ESP mint's retry would read them as spent elsewhere, and the holder would lose the notes. A crash after the record leaves a memo on notes that are not spent, which `/burns` never reports (it reports a memo only for notes that are spent) and the retry overwrites.
- A rollover (kind 5) and a spend (kind 14) burn notes over AIR and record no memo. Under the mint lock, before they burn anything, each **clears the memo of every input that is unspent at that moment** (`MeltLog::clear`, called from `server.rs`), the same notes `/melt` would record. The lock is held through the burn, so a note that is unspent at the clear and spent after it was burned by that request, and it reports no memo. A note that is already spent keeps its memo: it may be an exchange's real burn, and the retry needs it. Clearing before the burn is crash-safe: a crash leaves an unspent note with no memo, which is harmless. Without this, a memo left on a note by a refused melt (before `/melt` checked first) or by a crash would be reported for the note once a rollover or a spend had burned it, and the ESP mint would take it for the burn of its own exchange and sign it a second time (P1-01 of the item 31 review).
- So the memo on a spent note is the memo of the burn that spent it. **`/melt`, a rollover and a spend are the only burns** (`/melt` has two paths, current notes only and mixed with the previous set; the others are `rotation::rollover` and `rotation::spend`), and each either records its memo or clears the record first. The lock order is the mint, the burn memos, the rotor, the rollovers (`Rotating`); the log is the one `Rotating::melts` returns, which `/melt`, the rollover and the spend all use.
- A note that is already spent is never given a new memo. A second burn of it is refused as a double spend and the record stays as it was.
- A note spent with no record (spent by a rollover or a spend, or before the log existed) reports `spent: true` and `memo: null`. The ESP mint treats that as spent elsewhere.
- The file is a placeholder store, like `settlements.json`: rewritten in full on every burn (temporary file, fsync, rename, directory fsync). A missing file means no records, and an unreadable file is an error and never an empty log. It is covered by "Local store" in [ROADMAP.md](../sandbox-mint/ROADMAP.md).

## Using BTC to buy PSP

A payer buys PSP by sending a Bitcoin payment that carries a **claim key** in a data output. The payment carries no notes and no request: the mint decides what it is owed from the amount, at a price it locks, and the payer then claims exactly that many units, once. The PSP needs no connection from the payer to the mint. Everything it needs to know about the payment is on chain, and the answer is a record on the AIR server.

### The flow

1. The wallet makes a throwaway key, the **claim key**, for the purchase and saves its secret (`build_psp_payload`, see "Wallet" below). Its public half is the claim DID, 33 bytes.
2. The wallet seals the claim DID to the mint's DID public key. That is the whole payload (113 bytes on the chain, "Payload format"). The app's own Bitcoin wallet pays the PSP's address and puts the sealed payload in one data output.
3. At `settle.lock_confirmations` (1) the PSP opens the payload, takes the BTC/USD price and **locks** it in a settlement record for the transaction. The locked price gives the USD value, the units the payment is owed, and the confirmation tier ("Confirmation tiers").
4. At the confirmations of its tier (3, 4, 5 or 6 by default) the PSP writes the **owed record** to the AIR server, at an address only the claim key's holder can compute ("The owed record"). Nothing is signed yet.
5. The wallet reads the owed record and sends one **purchase claim** (kind 15): blinded outputs that add up to exactly the units owed, signed by the claim key. The PSP signs them and stores the answer ("The claim").

Before step 3 the scanner tries to decrypt the data output with the mint's DID secret key. Only what decrypts is read further. Anything else is not for this mint and is ignored.

### Settlement records

The PSP keeps one record per transaction, created when the payment is first seen with `settle.lock_confirmations` confirmations. Records are kept in `settlements.json` in the data directory, a JSON object with two members: `records` (txid to record) and `pruned` (what the mint keeps of the payments retention removed, see "Retention"). The file is a placeholder store. It is rewritten in full on every change: written to a temporary file, fsynced, renamed over the old file, and the directory fsynced. A missing file means no records yet, and an unreadable file is an error, never an empty store. This state probably needs to eventually "live on the air". A `settlements.json` from 0.7.x is not read and not migrated (a payment of that design has a different record); `serve` refuses to start and says so.

| Field | Meaning |
|---|---|
| `status` | `locked` (price taken, not yet at its tier), `owed` (the owed record exists), or `kept` (nothing is owed). |
| `locked_price_cents` | USD per BTC in whole cents, taken at the first sighting and never refreshed. |
| `late` | True if the price was locked later than the scan that should have seen the payment (a late scan locks a later price). |
| `value_sats` | What the payment paid the PSP's address. |
| `claim_did` | The claim key from the payload (absent when nothing readable). |
| `tier_confirmations` | The confirmations the payment must reach before it is owed, chosen at the lock and never changed. |
| `value_units`, `due_units` | Units the payment buys at the locked price (rounded down), and the units owed after the prepaid costs. |
| `read_prepaid_units`, `write_prepaid_units` | The costs that came off `value_units` (two reads, one write), fixed at the lock. |
| `kept_cents` | The sub-unit remainder the mint keeps. |
| `reason` | Why a `kept` payment is kept. |
| `delivery` | The owed record: the claim DID, its index, what it says (`outcome`), the sealed bytes, `delivered` and `abandoned` ("The owed record"). |
| `landed_at`, `open_until`, `expired_at` | When the owed record was found stored on the AIR server (the mint's clock, Unix seconds), the end of the claim window (`landed_at` plus 2,592,000, set in the same write as `landed_at` and the delivery's `delivered`), and when the expiry pass closed the window. All three are absent until the record lands: a payment whose record is not stored has no window, never expires and cannot be claimed. |
| `attempts`, `refusals` | Claims refused for their content, counted against `claim.max_attempts`, each with the hash of the refused request. |
| `claim_pending`, `claimed`, `claimed_at` | The accepted claim before it is signed (the full outputs), and the stored answer once it is. |

The settings that decide a payment's costs and tier are copied into the record when the price is locked, so a later change of a setting does not touch it. Everything the claim needs is in the record: a claim is checked against the record, never against the settings in force.

### Settlement rules

`settle.rs` is pure over its inputs (`settle_ruled`: the records, the payment, the price, the policy; it takes no clock, because no window is opened at settlement). It returns one of:

- **Waiting**: fewer confirmations than the lock needs. Nothing is stored.
- **PriceUnavailable**: the lock is due but the feeds did not give a usable price. Nothing is stored; the next scan tries again.
- **Locked**: the price is locked and the tier chosen, but the tier's confirmations are not there yet (or the payment left the chain). The record is stored with status `locked`.
- **Owed**: the tier is reached; the owed record is made (status `owed`).
- **Kept**: nothing is owed (below), stored with a reason and audited.
- **AlreadySettled**: the record is `owed` or `kept` already; nothing changes.

**Units.** One PSP unit is 10 US cents. The units a payment buys are `floor(sats × price_cents ÷ 10^9)`. The USD value used for the tier is `sats × price_cents ÷ 10^8` in whole cents, rounded down. The cost of the prepaid hooks (below) comes off the units, floored at 0.

**Kept.** A payment is kept, with no owed record and nothing for the payer to read, when:

- it has no single data output, or the one it has decrypts to something that is not a 33-byte claim key (a point on the curve). A payment whose data output does not decrypt at all is not this mint's: it is dropped by `seal::open_payloads` before settlement, with no record, no price fetch and no error. A payment with no data output, or more than one, has no payload and is kept at the lock with the reason "the transaction has no single data output"; one whose payload decrypts but is not a claim key is kept with "the payload could not be read" and the decode error.
- it owes **0 units**: it is worth under one unit, or the prepaid costs are as much as it buys (`Kept::NothingOwed`, reason "the payment buys N unit(s) at the locked price and the prepaid costs (C) leave nothing to claim"). No owed record is written, so the wallet, which cannot tell a payment still waiting for its tier from one that owes nothing, waits until it gives up. This is listed in the report as a design problem to decide (an owed record that says 0 would let the wallet stop).

A kept payment has a record, with status `kept` and the reason, only so `/audit` can show it (`kept`).

**The sub-unit remainder** (under 10 cents) is the mint's. It is not credited and not refunded; `kept_cents` records it in the settlement record and `/audit` adds it up (`subunit_kept_cents`). Units round down, so the payer never receives more than was paid.

**A payment that leaves the chain, or never reaches its tier,** is not owed and is looked at again by every scan: a `locked` payment is listed with the pending ones (`Records::unsettled`) and passed to the node again, whether or not it is still in the wallet's recent transactions. Once the owed record is made it is not undone. A reorg deeper than the payment's tier, after that, is the mint's loss; the tiers are exactly how deep the mint accepts.

**No tolerance and no target.** A payment is never matched against a request, so there is no underpayment, overpayment, credit, reconciliation or refusal. The payer gets what the money buys at the locked price, rounded down, or (if it buys nothing, or could not be read) nothing. Never refunded (decided 2026-10-22, ROADMAP.md "Shared items").

### Confirmation tiers

The price locks at one confirmation (`settle.lock_confirmations`), so a payer who sends a large amount does not get a later price just because it waits for depth. What the payment has to wait for, before the mint writes an owed record, depends on its locked USD value:

| Locked value | Confirmations |
|---|---|
| under $10,000 | 3 (`settle.base_confirmations`) |
| $10,000 up to $50,000 | 4 |
| $50,000 up to $100,000 | 5 |
| $100,000 and over | 6 |

Those are the defaults of `settle.base_confirmations` and `settle.confirmation_tiers` (`10000:4,50000:5,100000:6`). The comparison is `>=` on whole cents: $9,999.99 is the base tier and $10,000.00 is the next. The tiers are validated at start and on reload: thresholds ascend, confirmations do not decrease, every tier is at least `settle.lock_confirmations` and at most 1,000. The scan asks `listsinceblock` for the **highest** tier's confirmations as its `target_confirmations`, so a payment at any tier is seen at the depth it needs. The tier is stored in the record at the lock; a payment locked under one table is not moved to another when the settings are changed.

*Why.* A deeper reorg takes a larger payment from the mint after it has written a record that cannot be undone. The tier is the depth the mint is prepared to be wrong about, scaled to what it risks. It is a setting because the right depth is the operator's call.

### Retention

`settlements.json` is rewritten whole on every change, so it must not grow without limit. Two settings bound it, and for each **0 = keep everything**.

**Retention.** `settle.retention_days` (90 by default; 0, or 30 to 3,650; reloads live) is how long a payment stays in the file after it **finished**, counted from the time that finished it (`Record::finished_at`): **claimed** (`claimed_at`), **expired** (`expired_at`), **kept** with nothing owed (`kept_at`, set when `settle_ruled` keeps it) or **abandoned** (`delivery.abandoned_at`, set in the same write as `abandoned` when the deliverer gives up on a record whose cell holds another record or whose claim DID cannot be sealed to). `service::expire` (the step after every scan) calls `Records::prune(now, retention_secs, horizon_secs)`, which removes the payments for which `time + retention <= now`, in one write. A payment that is `locked`, open, landed and unclaimed, not stored on AIR yet and not given up on, or has a claim pending is never removed. A finished payment with no time to age it by is left alone and not guessed at. With retention 0 `prune` returns at once: nothing is removed, no marker is made, the cutoff below does not move. The claim window is unchanged by this setting: a payment still expires on time, and the expired record simply stays.

The file is `{"records": {txid: Record}, "pruned": {"txids": {txid: block_time}, "owed": {claim_hex: {"count", "last_block_time"}}, "totals": Claims, "cutoff": u64}}`. What the mint needs of a removed payment goes into `pruned` in the **same write** that removes it:

- **The txid, with its block time,** goes on the list, so a scan that sees the payment again (it is still in the wallet) is answered `Settlement::Pruned` and not owed a second time (`Records::was_pruned`, checked first in `settle_ruled`; the answer is its own variant so that a pruned kept payment is not reported as owed).
- **The owed-index counter.** `owed[claim]` counts the owed records of that claim DID that were removed, with the newest block time among them; the next index for that claim DID is that count plus the records still in the file (`Records::next_owed_index`), so an index, and with it a cell and a record id, is not reused while the claim key may still be read.
- **The `/audit` aggregate.** The removed payment's share of the `claims` totals is added to `totals`, and `Records::claims` adds the file's payments to it, so `claimed`, `expired`, `abandoned`, `kept` and the prepaid costs never shrink. A removed abandoned payment's share is added to `abandoned`, where it was shown before it was removed.
- **A resend after the prune** names a record that is no longer there and is ignored as `unknown_owed`, not counted.

**The horizon.** The markers would grow with the payments for ever (about 90 bytes for a txid, about 150 for a claim DID's counter), so they are bounded too. `settle.prune_horizon_days` (210 by default; 0, or at least 2 x retention + 30 and at most 10,000; reloads live) sets `pruned.cutoff` (Unix seconds): at each `prune` pass it becomes `max(cutoff, now - horizon)`, so it only moves forward. Then every txid on the list whose block time is before the cutoff is dropped, and so is every claim DID's counter whose newest block time is before the cutoff **and** that has no record left in the file (while one is, the counter is still needed). The cutoff is kept in memory on every pass and written with the next write of the file, at the latest in the same write as a drop, so a dropped marker is always covered by a cutoff that is on disk. `settle_ruled` ignores a payment that has no record and whose block time (`Received::block_time`, from `gettransaction`'s `blocktime`, kept on `Record::block_time`) is before the cutoff, next to the `was_pruned` check: nothing is stored and no price is asked, and `service::cycle` counts such payments and says it once per pass (`Settlement::BeyondHorizon`). A payment with a record is never affected, whatever its age. The floor of 2 x retention + 30 days is checked together with the retention at start and on reload (`Config::validate`; a reload that breaks it changes nothing), and the message names both settings. With horizon 0 the cutoff never moves and nothing is dropped. With retention 0 the floor is not checked (any horizon up to 10,000 is accepted), since there is nothing to cap.

*What holds.* (1) **Never owed twice:** a payment is in the file, on the list, or older than the cutoff, and the cutoff never moves back, so a payment cannot be locked again; raising the horizon by a reload does not revive a dropped marker, since the cutoff is not recomputed backwards. (2) **The `/audit` totals never shrink:** the aggregate is fixed-size and never dropped. (3) **Index reuse beyond the horizon is harmless:** the payer keeps the one-time claim key only until its first read plus 30 days, the counter is dropped only when its newest payment is more than the horizon old, and the horizon is at least twice the retention plus the 30-day window. (4) **The cost:** a payment first seen after the cutoff has passed its block (the scan blind to it for longer than the horizon, or a rescan of very old blocks) is ignored and not settled; the pass says how many. The cutoff moves only at the end of a prune pass (after the scan), so a restart alone does not cause it. The file is bounded by the payments of the last horizon (their markers), the live payments and the finished ones of the last retention, plus the fixed-size totals. A file with an older shape (a bare txid-to-record map, or a list of txids) is not read; this was not released.

### The owed record

The mint delivers what a payment is owed as **one write-once record on the SPI's AIR server** (`air.server`, `air.host`), at an address only the claim key's holder and this mint can compute, and the mint pays for it: the payer needs no balance. The design and the reasons are `air-sandbox/REQUEST-DESIGN.md` section 18 and `sp_wire::air_request::delivery`; what is specific to this mint:

- **The address.** Cell *n* of a claim key is `sha256("sp-psp-owed-v0" || the mint's DID || the claim DID || n)`, where *n* is a `u32`. The claim DID is a one-off key of the payer's for this purchase, so the mint cannot link two purchases, and nobody who does not hold the claim key can compute the address. *n* is the number of owed records the mint has made for that claim DID (removed ones included, see "Retention"), counted from 0 and assigned when the owed record is made, under the records lock. The mint **writes the cells in index order**: see "Retry". The wallet reads cells 0, 1, 2 and so on until one is empty, and reads past a cell it cannot open.
- **The record id** is `sha256("sp-psp-owed-id-v0" || claim DID || n)`: the claim names the record it claims by this id. It does not include the mint's DID so the claim path does not need it.
- **The record** is a reply envelope signed by the mint's DID key (`mint_did_key.json`) and sealed to the claim DID. `Owed` carries the txid, the sats paid, `value_units` and the **terms** of the one claim: `send` (the AIR kind, 15), `kind`, `due_units`, `read_prepaid_units`, `write_prepaid_units`, `window_secs`, `max_attempts` and `on_expiry` (the notice that the mint keeps the bitcoin). It carries no keysets (the payer asks the current one with kind 4 right before it claims) and **no end time**: the record is sealed once and written with identical bytes at every retry, so it cannot state a date that a late write would pass. A wallet checks the signature, takes the terms as they are, and claims **as soon as it has read the record**, and keeps its claim key until its first read plus `window_secs`: the mint's deadline (`landed_at + window_secs`) is never earlier than that.
- **Copied payloads.** The payload is the claim key and nothing else, so a copied payload pays the claim key's holder every time. Two payments with one payload are two owed records, index 0 and 1, each claimable once. The copier gets nothing: the holder of the claim key is the payer it was meant for. This replaces the old one-payload-one-payment rule (`DuplicatePayment`).
- **Where it is kept.** The mint stores the sealed record in the payment's settlement record (`delivery`) in the same write as the status, before anything is sent. That is the only copy of the record the mint keeps. Delivery never blocks or undoes settlement.
- **Retry.** `delivery::Deliverer` writes every owed record that is not stored yet after every scan (`run` once; `serve` on every cycle, whether or not the scan worked). **In index order:** a pass writes, for each claim DID, only the lowest owed record that is not stored yet (`Records::next_to_deliver`); index 1 is not tried while index 0 is waiting, failing or not yet written, so a wallet that stops at the first empty cell never stops before a record that lands later. A record the mint gave up on (`abandoned`: a different record is in its cell) is not undelivered and does not hold the later ones back. A failed write is tried again after a wait that doubles from 10 seconds to 15 minutes; the waits are in memory, so a restart tries everything at once, and a record is tried until it is stored, across restarts. The sealed bytes are made on the first try and saved in the record *before* they are written, so every retry writes the same bytes. The AIR server answers a write to a taken cell with what it holds: the same bytes mean an unacknowledged write got through (delivered), different bytes are reported and left alone (`abandoned`, never overwritten). Exactly one record is ever written to a cell.
- **The window starts when the record lands.** `Records::land(txid, now)` runs when the deliverer has the record stored on AIR (written, or found stored with the same bytes): in **one write** it sets `delivered`, `landed_at = now` and `open_until = now + sp_wire::psp::CLAIM_WINDOW_SECS` (2,592,000 s, 30 days; a constant in sp-wire, not a setting, so a wallet and the mint cannot disagree about it). The wall clock comes in as an argument (`Deliverer::pass_shared(records, now: Instant, wall_now)`; `Instant` stays the clock of the retry waits). `put_delivery` refuses to mark a record delivered without it. An AIR server that is down for a long time costs the payer nothing: no window has started. The expiry pass looks only at landed records, so a record that never lands never expires, and a claim for it is ignored as `unknown_owed` and not counted: the payer cannot have read it.
- **No new settings.** The deliverer uses `air.server`, `air.host` and `air.timeout_secs` (which also bounds a connection), and the mint's DID key. With `air.server` or `air.host` empty (`run` without them) nothing is delivered and a note says how many are waiting.

### The claim

One request, `KIND_PSP_CLAIM` (15), sent by the holder of the claim key, claims the units the owed record names. The code is `claim.rs` (the checks and the signing), `settle.rs` (the amounts, fixed at the lock), `records.rs` (the stored state) and `server::claim_served` (the listener's entry). It is one claim per owed record: whole, or not at all, in one window, with a small number of attempts, nothing refunded.

**Who may ask.** AIR clients are anonymous, so the request carries a BIP340 signature by the claim key (`ClaimRequest::digest(&self, psp)`, tag `psp-mint/claim/v1`: **this mint's DID**, the claim key, the record id, the keyset and every output's amount and blind nonce; the mint passes its own DID (`server::ClaimDesk`), so a claim signed for another PSP fails here, and a claim cannot be replayed to a second mint that holds the same claim DID and record id). The record id and the claim DID in the request pick the owed record. The envelope's sender is not checked. A mis-signed request is **dropped before any lock is taken and before anything is read**, and it is not counted against anyone.

**The terms are the record's.** A claim is checked against the terms stored in the settlement record when it was made, never against the settings now in force.

**Order of checks**, cheapest first, with nothing signed until the last:

1. Shape (`check_shape`): size, at least one output, a keyset named. No lock.
2. The **signature**, before anything else. No lock.
3. Under the locks: the owed record it names (`unknown_owed`) and its status. A record that is not stored on AIR yet (`landed_at` absent) is `unknown_owed` too, not counted: the payer cannot have read it.
4. A claim already accepted: the identical request (same hash) gets the **stored answer**, byte for byte; any other claim for that record is refused (`already_claimed`, not counted). A pending claim with the same hash is finished; a different one while one is pending is refused `in_progress`.
5. A request that is a resend of one already refused for its content is refused again, and not counted again.
6. The window: at or after `open_until` (the landing plus 30 days), or for a record the expiry pass closed, `claim_expired`. A claim accepted before `open_until` is finished after it.
7. The cap: `claim.max_attempts` counted refusals (`too_many_attempts`).
8. The keyset: it must be the **current** one. The previous set gets `keyset_not_current`, a retired one `keyset_retired`, an unknown one `unknown_keyset`; **none of the three is counted**, so a rotation does not use up the payer's attempts.
9. The content: the denominations exist (`unknown_denomination`), no blind nonce twice (`duplicate_blind_nonce`), the outputs add up to **exactly** `due_units` (`wrong_total`: one unit under and one over are both refused, nothing signed), no blind nonce the mint ever signed (`blind_nonce_used`). A refusal here is one **counted attempt**, written with the hash of the request.
10. The accepted claim is saved on the record with its full outputs (`claim_pending`) in **one write**. Then `finish` signs.

**No refusal replies.** An accepted claim gets a `ClaimResponse` (the signatures, the keysets, `issued_units`, `read_prepaid_units` and `write_prepaid_units`); anything else gets no reply at all and the reason is in the mint's log, with its code. A wallet that gets nothing for a while sends the identical claim again. The reasons for silence: a reply would tell an attacker which key signed, and there is nobody to ask who would not be the claim key's holder.

**Crash safety, as the rollover's.** (1) The accepted claim is saved as `claim_pending` before anything is signed: a crash before this signs nothing. (2) The outputs are signed with `issue_with_key`; a crash in the middle leaves some signed and counted by the mint. (3) The close is **one** `Records::put`: the answer by request hash (`claimed`), `claimed_at`, the pending entry cleared. (4) An identical resend after (3) gets the stored answer. A crash after (1) or (2) is finished by `service::recover` **without the wallet sending the claim again**: an output whose blind nonce the mint already signed is signed again with `bdhke::sign_message` (the same key gives the same signature, and the mint's issued total counts it once), and the answer is stored. A failed answer write is an error: the claim stays pending and is finished at the next pass.

- **Where recovery runs.** At startup, as `serve` opens (before the listener takes a request), and at the top of every scan pass. It takes the locks in the usual order (records, mint, rotor), one claim at a time, tries every claim, and returns the first error after the last. The key set that signs is the **current** one at the time of the recovery, not the one the claim named: normally the same. If the mint rotated between the acceptance and the recovery (a crash *and* a rotation in between, which the 720-hour floor makes rare), the answer names the new set and the wallet unblinds with that set's keys. Outputs the old set had already signed before the crash count in its issued total and no wallet got them; the new set signs the whole claim again and counts it in its own total. So `/audit`'s issued total can exceed the claimed units by at most **the outputs of the claims pending across a rotation**, each counted as far as the old set had signed it (at most those claims' `due_units`): normally no claim, since a claim is accepted and answered in one step and recovery runs before the keysets rotate; one after a crash, since claims are taken one at a time under the records lock; and a claim whose answer write failed also stays pending with every output signed, for as long as recovery keeps failing, while a rotation asked for through the API (`server.rs`) can come in that time. No counter is kept and the mint does not correct the sum; the claimed units (`claims.claimed.units`) are exact. The previous set exists for legacy notes (rollover, spend, check-state), never for a claim.
- **Expiry replaces forfeiture.** After every scan, `Records::expire_unclaimed(now)` marks each owed payment that has landed on AIR, whose `open_until` is `now` or earlier and that is not claimed and has no pending claim: `expired_at` is set, the mint keeps the bitcoin. A record that has not landed has no `open_until` and is never expired. A claim that was accepted before `open_until` is not expired; it is finished. The boundary is inclusive for the expiry pass and a claim at exactly `open_until` is refused, so the mint and the wallet agree.
- **Locks.** The records are shared between the scan thread (settle, deliver, expire, recover) and the AIR listener (`SharedRecords`, an `Arc<Mutex<Records>>`). The order is always **records, then the mint, then the burn memos, then the rotor, then the rollovers** (a call takes only some of them, in this order: `/melt`, a rollover and a spend take the memos, because they record or clear a memo before they burn). The scan takes the records lock per payment, and holds it neither across the wallet scan, the price fetch, nor a delivery write to the AIR server (`Deliverer::pass_shared` plans and applies under the lock and writes outside it), so a claim never waits for the network. The AIR entry checks size, shape and signature before it takes any lock. A poisoned records lock is an error on every path that needs it, and nothing is signed.
- **Audit.** `/audit` gets a `claims` section (added by a middleware around the audit routes, `server::router_live`, because the audit body itself is mint-core's `AuditResponse`, which this mint does not change): `claimed`, `unclaimed` (owed and claimable: still open, or accepted and being finished), `expired` and `abandoned` (owed, but the owed record could never be written, so the payer cannot claim it; the mint keeps the bitcoin), each with `payments`, `sats` and `units`; `kept` (the same three numbers: payments kept with nothing owed); `subunit_kept_cents`; `read_prepaid_units` and `write_prepaid_units` (over the claimed payments); and `refused_attempts`. The figures include the payments retention has removed (`Records::claims` adds the aggregate kept in `pruned.totals`), so they never shrink; see "Retention".
- **Not built.** The prepaid AIR reads and the write are amounts only: the PSP records what it would pay and does not yet pay it (it waits on AIR). The answer to the claim is the reply to the request, not a record in a separate cell. Payments kept are still not refunded.

### Fees

The PSP has no fee of its own besides the BTC purchase. Fees at the later layers (exchange to ESP, transfer, and FSP use) are paid in AIR currency and charged by AIR messaging, not by the mints. The only explicit mint fees are the BTC at PSP purchase and the ESP redeem fee. A separate fee on top of the 1 USD rate is not defined or implemented.

**The prepaid hooks.** Two settings, `delivery.read_fee` (formerly the first-read prepay, still the same name) and `claim.write_fee` (formerly `reconciliation.write_fee`; renamed because the claim is the only write), are costs the SPI prepays on the payer's behalf for AIR: the payer reads the owed record and reads the answer (two reads), and sends the claim (one write). They default to 0 and are taken from the units the payment is owed: `due_units = floor(value_units - 2 × read_fee - write_fee, 0)`. They are copied into the record at the lock, shown in the owed record and the answer, and added up in `/audit` for the claimed payments. A payment whose costs equal or exceed what it buys owes 0 and is kept. Only the amounts are recorded; the prepaid AIR calls are not built.

### Price

The price is locked when a payment is first seen with `settle.lock_confirmations` confirmations or more and has no record yet. The first run that sees the transaction fetches the price, once per run, and stores it in the record. The tier and the units use the stored price and never a live one. The PSP does not poll the exchanges.

| Source | Endpoint | Price | Quote time |
|---|---|---|---|
| Coinbase | `https://api.exchange.coinbase.com/products/BTC-USD/ticker` | `price` | `time`, ISO 8601 UTC |
| Bitstamp | `https://www.bitstamp.net/api/v2/ticker/btcusd/` | `last` | `timestamp`, unix seconds |
| Gemini | `https://api.gemini.com/v1/pubticker/btcusd` | `last` | `volume.timestamp`, unix milliseconds |

All three are public, need no key, and the price used is the last trade. The sources and URLs are fixed in the code (`src/price.rs`) and are not settings: changing them means changing code. Gemini's timestamp is undocumented and aligned to the minute, so it only bounds the age of its quote to about a minute.

- A source is excluded if it errors, returns no price, or its quote time is more than 120 seconds from now (`price.max_age_secs`, `PSP_PRICE_MAX_AGE_SECS`).
- 3 usable prices: take the median.
- 2 usable prices: average them (rounded down). If they differ by more than 2% of the lower one (`price.max_spread_bps`, `PSP_PRICE_MAX_SPREAD_BPS`, 200), wait and retry on the next run.
- 1 or 0 usable prices: wait and retry on the next run. The PSP never settles on a single feed.
- Prices are whole US cents per BTC. Decimal strings are parsed to cents with no floating point, and anything past the second decimal is dropped.

The price is a live ticker price taken when the run sees the payment, not a block-time price. The PSP does not use block timestamps or historical candles, because miners can skew a block's timestamp by about 2 hours. This is why the PSP must scan every few minutes (`serve` does, every 120 seconds by default): the price is taken at the first scan that sees the payment at 1 confirmation, and a run that comes late locks a later price and marks the record `late`. The rule is in `src/price.rs`, with the aggregation as a pure tested function.

### Payload format

This is the payload before encryption. It is what the PSP decodes after it has decrypted the data output: **the claim DID alone, 33 bytes**, a compressed public key (a point on the curve; bytes that are not one are not a payload, and the payment is kept as unreadable). There is no length byte, no output count, no notes and no version byte: the wire version is the crate's `WIRE_VERSION`, now 4. Payloads of version 3 (a reply DID and blinded outputs) do not decode as 33 bytes and are kept as unreadable. Nothing in the payload limits how much a payment can buy, and nothing here claims a limit on the size of a data output: the payload is the same size for every purchase.

### Encryption

The payload is encrypted to the mint's DID public key, and only the mint's DID secret key can decrypt it. The cipher is AIR's (2.0.3, and unchanged in 2.1.0), its `PublicKey` and `SecretKey`, which `sp-wire` re-exports, not a new scheme: `PublicKey::encrypt` seals bytes to a public key and `SecretKey::decrypt` opens them. It does an ElligatorSwift key exchange with a fresh sender key for every message, then ChaCha20-Poly1305. No payer signature is needed.

- **Wallet.** Seal the claim DID to the mint's published DID public key and put the result in the data output. The wallet library's `build_psp_payload` does all of it (below). `psp-mint encrypt <mint pubkey hex> <payload hex>` seals a ready payload, for testing.
- **Mint.** The scanner tries to decrypt each data output with the mint's DID secret key and reads only what decrypts. Anything that fails is not for this mint. It is ignored without a record, a price fetch or an error. This covers a payload sealed to another key, a tampered one, and a cleartext one. Nothing is accepted in cleartext.
- **Wire format.** `64-byte ElligatorSwift sender key || 16-byte tag || ciphertext`, and nothing else. There is no length byte and no framing, so a sealed payload is always 80 bytes longer than the payload: **113 bytes** for the 33-byte claim DID, and anything under 81 bytes cannot be a sealed payload. A sealed payload is a constant-size envelope around a ciphertext as long as the payload; bytes added or removed make the tag fail, so they are rejected. The sender key is an ElligatorSwift encoding, which looks like random bytes.
- **Keys.** The mint's DID key pair is a local file, `mint_did_key.json`, in the data directory, with `0600` permissions. It is made on first use and never overwritten. `psp-mint pubkey` prints the public half, 33 bytes in hex, for wallets to seal to. Moving the key into the AIR keystore is deferred.

### Wallet

The `ecash-wallet` crate (a sibling folder, with a thin command line) is the client for this mint. Its hook for an AIR app is expected to become (pass 2; the wallet in the tree still builds the old payload):

```
build_psp_payload(mint_did_pubkey) -> PurchaseBuild { claim key, payload }
```

The call makes the claim key for the purchase, saves its secret in the wallet file before anything is returned, seals the claim DID to `mint_did_pubkey` with `seal::encrypt` and returns the bytes for the data output. The wallet holds no BTC wallet, so the caller's own Bitcoin wallet sends the payment. The wallet then reads the owed records from the addresses it computes (cells 0, 1, 2, … until one is empty), checks the mint's signature, and for each record it has not claimed it blinds outputs that add up to `due_units` exactly, signs the claim with the claim key and sends kind 15. From the answer it pairs the signatures with its saved outputs by blind nonce, unblinds them with the keys in the answer, and stores the notes. A claim that gets no reply is sent again, identical.

The wallet calls this crate's seal by path, and sp-wire's `payload` and `psp` modules for the formats, so the format is defined once, in sp-wire.

## Networks

*Why mainnet by default and a flag for the rest:* the default is what a real operator runs; a test network is a choice made on purpose.

**The scan.** Each scan reads every wallet transaction since the last block it finished at (`listsinceblock`), however many there are, plus every payment that is not yet settled, so nothing is missed in a burst and a payment waiting for confirmations is looked at again. The block is kept in `scan_checkpoint.json` in the network folder, written only after a scan succeeds, so a restart carries on where it stopped. A reorg is handled: transactions removed from the chain are reported by the node and checked again, and a payment is never settled twice. A damaged checkpoint is an error, never replaced.

## Caps on sizes and fees

Every size ceiling has a hard cap, checked when the settings load (every command): a value outside its range stops the mint with `<key> = <value> is out of range: it must be from <low> to <high> (<why>)`. Defaults are inside every range. The two flat fees have no cap of their own (below), and they stay 0 by default. No setting should reach a value that breaks the mint's own routes.

**Request ceilings: 16 KiB to 15 MiB** (`server.melt_max_request_bytes`, `server.rollover_max_request_bytes`, `server.burns_max_request_bytes`, `server.check_state_max_request_bytes`; the floor was 4096 and the cap 1 GiB).

- *The cap, 15 MiB (15,728,640 bytes),* is what one AIR message carries: 16 MiB, less 1 MiB kept for the envelope, its seal and AIR's framing (the same figure as esp-mint's `AIR_MESSAGE_CAP` less `AIR_ROOM`). A ceiling above it would let the mint take a request no wallet can send. The two loopback routes are called by esp-mint, whose `exchange.max_items` cap of 25,000 makes the largest melt 25,000 notes at 367 bytes (a note 347, its keyset 19, JSON compact) = about 9.2 MB, which fits.
- *The floor, 16 KiB (16,384),* is twice the widest one-note request, measured from the real types with each field at its widest (20-digit amounts, hex keys): a spend with one note, a 256-byte memo and 64 change outputs is 8,090 bytes; a rollover of one note with 64 outputs is 7,905; a one-note melt is 465. Sixty-four is the most outputs one amount needs, since a `u64` splits into at most 64 powers of two.

**`rollover.max_items`: 64 to 25,000** (was 1 to 100,000). The floor is those 64 outputs, so a one-note spend is never over the count (the most change one note can need is 63 outputs, for a note of 2^63, the largest denomination every keyset has: one key per power of two, 2^0 to 2^63, 64 keys, as fsp-mint's; it is not a setting). The cap is what fits the ceiling cap: one note and one output are 482 bytes together in JSON, so 25,000 of each are 12.05 MB, under 15 MiB; the old 100,000 would be 48 MB, which no AIR message carries. Both facts are `const` assertions in `config.rs`.

**The two flat fees: no cap.** `claim.write_fee` and `delivery.read_fee` are flat amounts in PSP units, not per-byte rates (decided in regtest round 1, ROADMAP item 18, by David). An earlier draft of this round capped them so that their total could never take more than the 1 unit (10 cents) of the smallest purchase. That is gone: a PSP unit cannot be split, and nothing stops a buyer from making a small purchase anyway, even though it is not recommended. **Raising these fees can eat up a small PSP purchase.** Twice `delivery.read_fee` (the owed record and the answer are each read once) and `claim.write_fee` come off the units the payment buys, and the subtraction stops at 0 (`saturating_sub` in `settle.rs`). A purchase they eat up owes 0 units and is kept: no owed record is written and `/audit` counts it under `kept`. Nothing overflows and nothing unpaid is signed. The only bound left is `MAX_FEE_UNITS`, 2^62 PSP units, which keeps the sums far from `u64::MAX`; it is not a limit on what a mint should charge.

**Checked and left alone:** `claim.max_attempts` (1 to 1000), the price, scan, confirmation (`settle.*`, validated together at start) and AIR settings, `rotation.*`, `server.bind` and the storage settings. There is no PSP fee rate per byte; the BTC price is the PSP's only price.

**Tests.** One per cap: a value past it (and, for a ceiling and the item count, one below its floor) is refused when the settings load. There is no test of a value between the ends. The fees' only bound, 2^62, is tested by `config_refuses_a_fee_over_the_most_a_fee_may_be` in `tests/cli.rs`.

## Settings

Every setting, its environment variable, default, range and whether it reloads live is the table in the [README](README.md), "Settings"; `tests/docs.rs` fails if the table and the code disagree. The settings that shape the claim design are `settle.lock_confirmations`, `settle.base_confirmations`, `settle.confirmation_tiers` ("Confirmation tiers"), `claim.max_attempts`, `claim.write_fee` and `delivery.read_fee` ("The claim", "Fees"). The claim window is not a setting: it is `sp_wire::psp::CLAIM_WINDOW_SECS`, so the mint and the wallet read the same figure. A setting removed in 0.8.0 stops the mint with a message that names it and what replaces it, so an old config file is never silently ignored.

## The AIR listener (mint info, keys, keysets, rotation, rollover, check-state, spend)

These seven are the calls a wallet makes. They were HTTP routes before 0.5.0 and are only AIR now; `/melt`, `/burns`, `/audit` and `/health` stay on a loopback HTTP server for the SPI and the operator.

The long form is `air-sandbox/REQUEST-DESIGN.md` in sandbox-mint; the wire is `sp_wire::air_request`. What is specific to this mint:

- **Placement.** One module, `air_listener.rs`, and one thread started by `serve` after the HTTP server's pieces exist, with a runtime of its own so that the HTTP runtime and the listener never share a thread. It always runs (there is no `air.enabled`): wallets reach the mint over AIR and only over AIR, so a `serve` without a listener would be a mint nobody can use, and `serve` refuses to start without `air.server` and `air.host`. What it answers with is `server::air_served_with(state, rot, records, health, limits, kind, body)`: for mint info `Health::mint_info`, the same report as `GET /health` (so a wallet sees `scan_stale` or `mint_lock_poisoned` over AIR exactly when `/health` would say so); for keys, keysets and rotation the response structs (`keys_response`, `keysets_response`, `rotation_response`), serialised with `serde_json`. The HTTP routes these calls once had are gone; the functions stayed.
- **Why the listener takes a `serve` function.** `air_listener::run` was given the mint-info closure; it is given a `Serve` now (`Fn(u8) -> Option<Served>`: a kind to a body, to "unavailable", or to `None` for a kind not served, which is skipped). `air_listener` knows nothing of the mint's state, and `mint_info_only` keeps the listener's tests free of a mint. The state comes from `serve` in `main.rs` (`start_air_listener` also takes the rotation handle and the shared records).
- **Unavailable instead of silence.** Where a route would answer 500, the listener signs a reply with status `unavailable` and no body. Silence would cost the wallet its whole tries (90 s at the defaults) for a mint that has already said it cannot answer; a signed refusal cannot be forged, and the reply cell is write-once so that request is over (the wallet makes a new one next time).
- **What a request can cost the mint.** Anyone can write a mailbox slot, so anyone can make the mint serve its keys; the keys are public, the work is one short lock and a serialisation, and the held reads bound how far ahead the listener looks, and a slot is answered once.
- **Why create-first.** The reply cell is write-once. Writing first and treating a stored record coming back as "already answered" avoids a read-then-write race between two listeners or a copied cell, and it makes a retry harmless. Mint info is a pure function of state, so answering twice is also harmless; the cell keeps the first.
- **The counter is local state, not mint state.** `air_mailbox_next` lives with the other local files of the network's data folder and is not under the storage policy (`storage.mint_state`): it holds no money and no spend, and losing it only costs a probe from slot 0 (each answered slot's reply cell is taken, so it is passed over). It is therefore not replicated to the storage services.
- **Supervision.** The AIR client reconnects on its own after a server restart, but it can also give up for good (a refused session closes every held read at once), and nothing tells the mint. So the listener counts how many held reads end: more than five within ten seconds, and it stops with a message. These two numbers and the three tries to write a reply are constants of the listener, not settings. When it does, the process exits with status 1: a mint that no wallet can reach is not running, and a supervisor restarts it (the listener resumes from its counter). The HTTP side is local to the SPI and is not what a wallet needs.
- **Limits.** K held reads must stay under the AIR server's 256 per session (the 257th is refused and the session closed), so `air.held_reads` stops at 200. A held read costs the server about 2 KB.
- **Rollover and check-state (the calls with a body).** `server::air_served_with(state, rot, records, health, limits, kind, body)` also serves kinds 5 and 6. `post_served` is the one place that does what a route does around the call: the body ceiling first (the `413` JSON, `too_large_body`, which `/melt` and `/burns` share), then the parse (`malformed_request` if it fails), then `rollover_response` or `check_state_response`. What the call refuses with a `4xx` becomes `Served::Refused(body)`, the JSON with `error` and `code`; a `5xx` becomes `Unavailable` (nothing of the mint's state is told, and a retry is safe).
- **Idempotency over AIR is the rollover's own.** `rotation::rollover` stores its answer by the request hash, with the request marked pending before any note is spent and the answer stored before the notes are marked, so serving the same body again (a retry in another slot, a replay of a slot after a crash between answering and writing `next`, a wallet that starts over with a new request id) returns the stored answer and touches no note. The listener needed no new mechanism: it already creates the reply first and treats `Taken` as answered, and a replay of a slot calls `serve` again, which is safe because `serve` is idempotent for these calls. A test copies a request into a second slot and checks that the first reply stays and nothing is spent twice.
- **Cost.** A rollover runs on the listener's thread and holds the mint lock while it runs (a full 1000-note rollover verifies and signs in under a second in the test); the listener reads no further slots meanwhile, and the HTTP side waits for the lock as it does for the scanner. The reply cell, not the listener, carries the answer back, so a slow rollover delays other AIR requests.
- **Privacy.** The request, body included, is sealed to the mint's DID, so the notes in a rollover are not visible to the AIR server; its size is.
- **Dying mid-request.** A panic in `serve` (for mint info, in the closure that builds the info) ends the listener thread the way a crash would, which is how the tests simulate a mint dying after it opened a request and before it replied.

## The spend (AIR kind 14)

A PSP spend with change is the one primitive that lets a wallet pay the SPI in PSP: notes in, change out, an amount `pay` that is the SPI's revenue: reissued to the SPI's own ecash-wallet, or burned, when `burn.enabled` is on and the SPI's wallet already holds `burn.threshold_psp` ("Reissuing the payment", below). Before it, the mint's only swap was the rollover, which must return exactly the input amounts, and `/melt`, which is a loopback route the ESP mint uses for exchanges. Nothing in this section attaches a spend to another request; that and the wallet side come later.

**Modelled on fsp-mint's spend** (kind 12): notes in, change out, an amount paid, a memo, and inputs = change + pay exactly, with a digest every input signs. It differs where psp-mint's structure does.

- **Keysets are the rollover's.** Each input names its keyset (`input_keysets`) and is verified, and looked up in the spent list, of the keyset it names. The change is signed by the one live keyset `keyset` names, the current or the previous (fsp-mint always signs with its current set, so its digest has no such field). The digest covers that keyset and length-prefixes the input keysets.
- **Spent lists are the mint's.** fsp-mint keeps its own spent lists in memory and a log per keyset, with group commit. The PSP's spent lists are mint-core's, one per generation, so a spend burns with `redeem_with_key` and signs with `issue_with_key`, as the rollover does, and takes the rollover's crash safety whole instead of a log of its own.
- **Where the state lives.** In `rollovers.json`, beside the rollover answers and under the same lock order: fields `spends` (answers by request hash) and `paid` (below), both always written with the rest of the file. A spend uses the file's `pending`, `burned` and `holds` under its own hash (the digest and request hash have their own tags, `psp-mint/spend/v1` and `psp-mint/spend-request/v1`, so the hashes never meet a rollover's). That is what makes one request in flight hold its notes against every other call: a rollover, a `/melt` or another spend naming a held note is refused `note_held`.
- **Ceilings are the rollover's** (`server.rollover_max_request_bytes`, `rollover.max_items`), and the memo's is the constant `MAX_SPEND_MEMO_BYTES` (256). A new setting for the spend can be added later; none was needed to make it possible to pay.
- **The memo is not recorded with the burn.** `/burns` tells the ESP mint whether a note was burned under *its* memo; a memo chosen by a payer must not be able to look like one. The memo is only in the digest, which is what binds it. A memo that an earlier `/melt` left on one of the spend's unspent notes is cleared before the notes are burned ("Burn memos"), so the spent notes report none.
- **A spend with no change** (`outputs` empty) names no change keyset and is answered with the current one.

**Check order, cheapest first, nothing burned before the last step:** shape and sizes with no lock (the note and change counts against the cap, the memo, the keysets named, `pay` > 0, then inputs = change + `pay` in `u128`, no note and no blind nonce twice); denominations; then under the mint lock the stored answer, the keysets, each note's proof and its spend signature over the digest, and the spent lists, then the output blind nonces (not signed already by the output set, `blind_nonce_used`; not held by an unfinished rollover or spend, `note_held`). A `pay` of 0 is refused `nothing_to_pay`: that request is a rollover.

**Crash safety** is the rollover's, and the argument is the same, step by step. (1) The request is saved as pending, with the notes and the output blind nonces it holds, and synced, before any note is burned: a crash before this burns nothing and holds nothing. (2) The notes are burned one at a time; a crash in the middle leaves some burned, and the same request sent again finds them spent, skips them, and burns the rest (a note spent and not held by this request is refused before the pending entry is written, so a half-burned request can only be this one). (3) The burn is recorded under the request hash. (4) The change is signed; `issue_with_key` claims a blind nonce atomically with the issued total, so a crash after a claim and before the reply leaves the output counted once, and the retry signs it again (signing is deterministic) without counting it. (5) The answer is stored and `pay` is added to `paid` **in one write** (temp file, fsync, rename), and the pending entry is removed in the same write. So a crash between the burn and the stored answer leaves a pending request whose retry finishes it, and the payment is counted exactly when the answer is stored, never twice and never lost. If the input keyset is deleted at a rotation in between, the retry is finished only with proof of the burn under its own hash (the `burned` mark, or the proof taken from the spent list when it was deleted and kept for this request alone), as for a rollover. A request pending forever (a payer that never retries) holds its notes; they are the payer's, who has the request.

**Reissuing the payment.** The mint does not keep the paid PSP as a balance of its own: it makes the notes and hands them to the SPI's ecash-wallet in a file. (1) `burn.enabled` and `burn.threshold_psp` decide, when the request is first saved, how much of `pay` is kept: all of it when burning is off, else `min(pay, threshold - held)` (`BurnPolicy::keep`); the rest is burned. **`held` is the SPI wallet's current PSP balance as the mint can know it** (`balance.rs`): the balance `spi` last published in `wallet_balance.json` (`{psp, reissued, at}`), plus the PSP the mint has reissued since that figure, that is `Rollovers::reissue_total()` now (paid and kept, plus the notes planned by spends in flight) less the `reissued` in the file. It is not a running total over the mint's life: once the wallet spends and `spi` publishes a lower balance, the room under the threshold opens again, and burning turns back off. The mint cannot see the wallet, so the figure is the SPI's to publish; `spi` reads the wallet balance first and the mint's `reissued` (`/audit`) second, so a note reissued between the two readings is in `reissued` but not in the balance, which counts it as not held and keeps more, never less: the error is always towards keeping the revenue. **No usable figure means no burning**: a missing, unreadable, malformed, stale (`burn.balance_max_age_secs`, 24 hours by default) or future-dated (more than a minute ahead) figure reissues the whole of `pay`, and the reason is logged once per change. The figure is read once per spend, before any lock is taken, and only while burning is on. **The figure must be current.** After the SPI's wallet spends, a figure published before the spend says the wallet holds more than it does, so `keep` is too small and the mint burns PSP that the wallet should have kept (the error is towards burning, not towards keeping). The figure only has to be close, so `spi` refreshes it on `spi collect` and `spi audit` and runs no timer (each publish runs `ecash-wallet balance`, which talks to the AIR server and the PSP). A figure older than `burn.balance_max_age_secs` (24 hours by default) is not trusted: the mint reissues everything and burns nothing, which is safe. A spend made with `ecash-wallet` directly is not seen until the next `collect` or `audit`. (2) The decision is saved with the request as `plans`: for each note, its amount, keyset, the secret of its nonce and the blinding factor, all drawn once. (3) When the change is signed, each planned note is blinded with its saved factor, issued (`issue_with_key`; a blind nonce already claimed before a crash is signed again, as the change is) and unblinded by the mint itself, so a retry after a crash makes the same notes. (4) The answer, `paid`, `paid_kept`, `paid_burned` and the notes are stored in the same write that removes the pending entry. (5) `flush_revenue` writes each spend's notes to `revenue/<request hash>.json` (a `sp_wire::psp::PspHandover`: the notes with their spend secrets, whoever holds the file holds the PSP) and then drops them from `rollovers.json`; the scan loop retries a write that failed, and a failed write costs the payer nothing. The file is mode 0640 in a folder of 0750 so the operator, in the service's group, can read it. `ecash-wallet receive-psp` swaps the notes at the mint for notes only the wallet knows, so a copy of a file already taken in is worth nothing. A planned note whose keyset has been deleted before the spend could be finished (a request resumed more than a key period later) is counted as burned.

**The audit.** `/audit` has `issued`, `redeemed` and `outstanding` as decimal strings (`"27670116110564327428"`; `u128`, summed over the live sets and the retired totals with checked adds, and an overflow is a `500` with a message, never a wrap or a panic). It has `paid`: the PSP units paid to the SPI by finished spends, with `burned` and `reissued` beside it. It is a counter of its own, kept beside the answers because the answers of a deleted keyset are pruned and the revenue must not shrink with them. The notes of a spend are `redeemed` whole, and the only part of `redeemed` that is revenue is `paid`: what the ESP mint burns through `/melt` for exchanges, and what a rollover burns and reissues, are in `redeemed` and not in `paid`. `paid` is `burned` plus `reissued`: with burning off (the default) every unit of `pay` is reissued, so it is part of `issued` again and `outstanding` does not fall by `pay`; it is the SPI's own PSP. (This replaces the decision of 2026-10-21 that the mints burn every PSP they are paid: ROADMAP 13(g) makes burning opt-in.) A purchase (PSP issued for bitcoin) is never touched by any of this.

## Storage policy (setting only)

`storage.mint_state` (`PSP_STORAGE_MINT_STATE`) names the AIR services that will keep this mint's state: an ordered list of service IDs, index 0 the primary and the rest secondaries in promotion order. A service ID is the service's AIR DID: a 33-byte compressed key in hex (66 characters, starting `02` or `03`). The 32-byte x-only form is refused with a message that says to use the DID. In the environment the IDs are comma-separated; in `psp-mint.toml` the value is an array of strings or one string. One entry is valid (that service holds the state and the mint keeps a local backup copy); empty, the default, means local only; at most 8, no duplicates, no empty entry. The parser and checks are `sp_wire::storage` (sp-wire), shared by all three mints and the wallet, so a list means the same thing everywhere.

This is configuration and validation only. **Nothing reads or writes the AIR yet:** the state is still in local files, whatever the list says. The mint logs the list at startup like any setting. What the list will do, and what the mint's storage layer must then provide (eight numbered requirements: 1 a spend is fsynced to the mint's own local copy before the mint answers, and copied to the backups afterwards, batched, never held for them; 2 a local backup copy with one service; 3 only the mint promotes a secondary and updates its config; 4 writes carry a sequence number, so a returning primary is overwritten from the working copy; 5 the wallet file carries a version and is merged; 6 networks stay apart; 7 the mint's own local copy is the primary, fsynced, with external services as backup only and no cap; 8 a request's finishing entry and its ledger movements are one atomic write, which only esp-mint's per-day ledger needs), is that list: it is the whole set, and nothing else is promised. That replication belongs in mint-core's storage layer and is a candidate for AIR upstream. The mint's own local copy is the primary and every listed service is a backup (decided 2026-10-17): every spend is fsynced before the mint answers and replicated to the backups while they are reachable; while every backup is unreachable, unreplicated spends are queued and copied out in order to the first backup that returns. There is no cap: the mint carries on with no limit and never refuses or holds spends for replication, and `/health` only reports a degraded state while backups are behind. None of this is built.

## Running as a service

`psp-mint serve` runs under `launchd` (macOS) or `systemd` (Linux) as a user that is not root, with its data directory (`PSP_DATA_DIR`), settings file (`PSP_CONFIG`) and network (`PSP_NETWORK`) named in an env file. The definitions, the install and uninstall steps and the health monitor are in the README of the SPI repository ("Running as services"): `spi install` generates the systemd units or launchd property lists, the env and settings files and the health monitor from its `spi.toml`, and prints the root steps to put them in place.

**Failure and restart.** `serve` exits with status 1 if the scan thread dies or the mint lock or the settlement records lock is poisoned, and the service manager starts it again after a delay (growing under systemd, fixed under launchd) and never gives up. Downtime is not free here: a payment is priced only when a scan sees it at 1 confirmation or later, so a long outage can cost a price lock. The restart is picked up from what is on disk by the rules of a crash: the scan checkpoint is written only after a successful pass, and a pass also re-reads every payment that is not yet settled (see "The scan"), so a restart misses nothing.

**Signals.** `serve` listens for four signals from the first moment, on streams made once and kept for the life of the process, so that none ever takes its default action (which ends the process) even while the mint is starting or between two openings of its data: `SIGHUP` reloads, `SIGUSR1` takes a snapshot, `SIGTERM` and `SIGINT` stop it. The README's "Reloading, restarting and snapshots" is the operator's view; this is why it works.

**Reloading.** `SIGHUP` re-reads `psp-mint.toml` and the process's environment (`config::Handle::reload`). Every setting whose `Spec::reload` is true applies at once: the new settings are one `Arc<Config>` that a scan pass takes once, the request ceilings and the burn rule are one `LiveLimits` that a request takes once when it is accepted, and the health allowance is one atomic in `Health` that the reload sets, so a request is answered with the values it began with. A reload that finds any problem changes nothing. A setting with `reload` false ("needs a restart") keeps its running value in the `Arc<Config>` (so the scan and the requests go on with the value the stores were opened with), and the reload hands back the value the file now gives it (`Reloaded::needs_restart`); `serve` logs which settings those are and that they wait for a restart. Nothing restarts the mint but the operator.

**Restarting.** A setting that needs a restart, and a new version, take effect when the process is stopped and started again: a brief downtime. A restart changes what the mint opens (a listening socket, key sets, a connection to the AIR server). The process stops as in "Stopping", the service manager (or `spi`) starts the new one, and it opens the data. No flush is needed: sled writes everything when the last handle to the database is dropped (`Tree::drop`, sled 0.34.7 `tree.rs:98`) and releases its file lock when the file is closed (`config.rs:579-610`, `fs2`). One process holds the mint's data, so the new process cannot start before the old one has stopped, which is why this is a downtime and not an overlap. (The 500 ms window in which sled's background flush can lose the last spent marks if the process *crashes* is a different matter: ROADMAP item 24. A stop is not a crash.) What a wallet sees: a request written while the mint is down waits in its mailbox slot on the AIR server (`Cache::message` stores it in the `private` table, immutable and with no expiry, `server.rs:843-891` of air_server 1.0.1, and a read of a slot that is not yet written is held until it is, `server.rs:588-651`) and is answered by the next listener. The counter `air_mailbox_next` is written after each finished slot, and the new listener resumes from it; a slot answered but not counted is read again and its reply cell, which is write-once (`server.rs:872`), makes the second answer a `Taken`: nothing is answered twice. The new AIR client gets a new session (a client process's session does not survive its own restart, air_server `deploy/README.md:81-83`), so the old session's held reads stay behind on the server until upstream item 17 cleans them up; at most `air.held_reads` per restart. The local API refuses connections while the process is down; its callers retry. `/health` reports `"version"`, which `spi upgrade` compares with the version it installed. A no-downtime upgrade (the same process, the socket passed on) was designed and is deferred to ROADMAP item 25.

Why each restart-only setting is not live:

| Setting | Why it needs a restart |
|---|---|
| `server.bind` | It is the listening socket, bound once for the life of the process and kept open across snapshots. |
| `bitcoin.network` | It names the network's data folder (`<base>/<network>/`) and the chain the mint verified bitcoind to be on at the start; a different network is a different mint's data. |
| `bitcoin.wallet` | It names the wallet the scan reads, verified at the start. The checkpoint is that wallet's progress: a different wallet's payments older than it are not seen unless `scan_checkpoint.json` is removed first (a full scan). A change is made on purpose, not live. |
| `rotation.activation_hours`, `rotation.period_hours` | The `Rotor` is opened with them and schedules from them; the key sets it holds follow the schedule. |
| `storage.mint_state` | Where the mint's state is kept: the stores are opened there. |
| `air.server`, `air.host` | The AIR connection and the mint's mailbox on that server: the listener and the deliverer are connected to it for their life. |
| `air.held_reads`, `air.timeout_secs` | The listener's window of held reads and its wait for a reply, fixed when it connects. |

`scan.health_intervals` and `scan.health_grace_secs` were restart-only while `Health` was built once with the staleness limit; `Health` now keeps the limit in an atomic and a reload sets it (with `scan.interval_secs`, which it depends on), so they reload live.

**Snapshots.** `SIGUSR1` runs the same quiesce as a stop, without ending the process: it copies the network's data folder to `snapshots/<UTC time>/` (modes 0700, every file and folder fsynced), then writes `snapshots/LATEST` last by a rename, then opens the mint again. The brief asked for a snapshot taken "under the mint lock"; this takes it with the threads stopped and the stores dropped instead, because only that guarantees that sled has written everything and that nobody has the files open, and a caller sees the same thing, a wait. The pause is the time to stop the scan pass in progress, plus the copy, which grows linearly with the size of the data folder (every byte is read, written and fsynced), plus sled's time to open the data again, which also grows with it. A failed copy is removed and `LATEST` is as it was; the mint opens its data again either way. The folder holds the mint's keys, so it is 0700 and is the operator's to move off the machine. A snapshot is the network's folder, not the settings file, and not the DID key outside it.

**Stopping.** `SIGTERM` and `SIGINT` run the quiesce and exit with status 0: the requests being answered finish, the scan finishes the pass it is in, every store is written and closed. In order, each step joined: the scan (it ends after the RPC it is in, at most `bitcoin.rpc_timeout_secs`, 30 s by default), the AIR listener (the slot it is answering), the local API (at most `DRAIN_SECS`, 30 s, then the runtime gets 5 s to drop what is left) and the watch thread (at most 1 s). The timeout on the drain is made inside the runtime (`runtime.block_on(async { timeout(..).await })`): made outside it, `tokio::time::timeout` panics with "there is no reactor running", which this process did on every stop until it was fixed (`tests/serve_process.rs` runs the real binary and checks status 0). After the threads are joined the stores must be held by nobody else; if a task still holds one, a snapshot is refused (the files are open, so the copy would not be whole and they cannot be opened again in this process) and the process exits with status 1 so that the service manager starts it again, and a plain stop logs a warning. A stop that does not end before the service manager's stop timeout is killed like a crash, which the checkpoint and the settlement records already cover; the service files give it 90 s, more than the sum of the waits above.

**Opening the data twice.** The database allows one process at a time, so a second process that starts while the first has the data open cannot open it; it exits with an error and the service manager starts it again. A restart never has two: the new process starts after the old one has stopped, and a snapshot opens the data again only after the stores were dropped. The storage that replaces sled has to give the same refusal or an equivalent single-writer guarantee, and the writes of the scan checkpoint, the settlement records and the melt memos have to be atomic (all or nothing) and durable once the call that made them returns, so that a restart sees each one whole or not at all.

**Health.** `GET /health` is `200` while the scanner is keeping up and the lock is sound and `503` otherwise. The health monitor that `spi install` sets up (`sp-health-monitor.sh`, see the SPI README, "The health monitor") polls it and reports or restarts a mint that stays unhealthy.
