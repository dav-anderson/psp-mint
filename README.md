# psp-mint

psp-mint is the Primary Service Point (PSP) mint. A payer buys PSP with a Bitcoin payment that carries a throwaway claim key, sealed to the mint, in a data output; the mint watches its own Bitcoin Core wallet, locks the BTC/USD price at 1 confirmation, and once the payment has the confirmations its value calls for (3, or 4, 5 or 6 for a large one) writes to the claim key what it owes. The payer claims exactly that many units, once, and the mint signs the blinded notes. 10 PSP = $1. The ESP mint burns PSP here when a holder exchanges it for ESP. The mint rotates its keys and keeps no more than two key sets.

## Building

psp-mint builds from GitHub as it is: `Cargo.toml` names mint-core at `v0.3.0` and `sp-wire` at `v0.6.0` (git tags), wire version 4, and the committed `Cargo.lock` matches. `sp-wire` holds the wire types this mint shares with the other mints and the wallet (see [DESIGN.md](DESIGN.md), "Wire format and versions"), and it pulls in AIR for the payload encryption and, through its `air-client` feature (the transport of the mint-info request, see "The AIR listener"), `air_server`. sp-wire pins AIR at `eae5133` (AIR 3.0.0 plus the `SecretKey` export, on AIR's branch `air3-export-secretkey`) and air_server at `v1.0.1`, which takes `air` from crates.io; the `[patch.crates-io]` block in `Cargo.toml` points that at the same AIR commit, or two `air` crates are built and their types do not match (a patch applies only in the crate being built, so sp-wire's own block does not reach this one). The listener is part of `serve` and always runs: `serve` will not start without `air.server` and `air.host`. To test against unpushed local copies of `sp-wire` or mint-core, `sandbox-mint/scripts/local-git.sh` points git at the local folders and their local tags.

## Run

```
cargo test
cargo run -- --regtest serve
```

Pick the network with `--mainnet` (the default), `--regtest`, `--signet` or `--testnet`. `serve` runs the AIR listener (the wallet's calls), the SPI's local HTTP API and the wallet scan on a timer. It needs `air.server` and `air.host` (`PSP_AIR_SERVER`, `PSP_AIR_HOST`). The full setup of a regtest node and wallets, and a purchase from payment to signatures, are in [REGTEST.md](REGTEST.md).

## Commands

| Command | What it does |
|---|---|
| `serve` | The AIR listener, the SPI's local HTTP API, the wallet scan and the delivery of each settled purchase's record, in one process. Needs `air.server` and `air.host`. |
| `run` (the default) | Scans the wallet once, settles what it can, delivers what it settled (when `air.server` and `air.host` are set; else it says how many are waiting) and exits. For testing. |
| `config` | Prints the settings in use and where each came from. |
| `pubkey` | Prints the mint's DID public key (66 hex characters), making the key file on first use. Wallets seal payloads to it. |
| `encrypt <mint pubkey hex> <payload hex>` | Seals a payload to a public key and prints it as hex, for testing. Takes exactly those two arguments; with any other number it says what it takes and exits 1. |
| `--help` | Prints the commands and exits. |
| `--version` | Prints the version of psp-mint, then the versions of sp-wire, mint-core and air that `Cargo.lock` locked for this build, one `name version` per line, and exits. It reads no settings and touches nothing, so it is safe while the mint serves. Build with `--locked` for the lines to be the ones used. |

## Networks

psp-mint runs on mainnet unless told otherwise. Pick the network with a flag, before or after the command: `--regtest`, `--signet` or `--testnet` (`--mainnet` is the default and may be given). The setting `bitcoin.network` (`PSP_NETWORK`: `main`, `regtest`, `signet`, `testnet`) does the same, and a flag wins over the file and the environment. `--testnet` is testnet3 (Bitcoin Core's `chain` `test`).

Each network has its own defaults, used unless `bitcoin.rpc_url`, `bitcoin.wallet` or `bitcoin.cookie` is set:

| Network | RPC port | Wallet | Cookie (macOS) | Cookie (Linux) |
|---|---|---|---|---|
| main | 8332 | `psp-main` | `~/Library/Application Support/Bitcoin/.cookie` | `~/.bitcoin/.cookie` |
| regtest | 18443 | `psp-regtest` | `~/Library/Application Support/Bitcoin/regtest/.cookie` | `~/.bitcoin/regtest/.cookie` |
| signet | 38332 | `psp-signet` | `~/Library/Application Support/Bitcoin/signet/.cookie` | `~/.bitcoin/signet/.cookie` |
| testnet | 18332 | `psp-testnet` | `~/Library/Application Support/Bitcoin/testnet3/.cookie` | `~/.bitcoin/testnet3/.cookie` |

The cookie default is chosen by the operating system the mint runs on (macOS, else the Linux path), matching where Bitcoin Core writes it. Testnet stays testnet3.

**Each network has its own data folder**, `~/.psp-mint/<network>` (`PSP_DATA_DIR` is the parent): keys, store, records and checkpoint never mix between networks. `serve`, `run` and `pubkey` print `psp-mint on <network>: data in <folder>` on stderr first, so `$(psp-mint pubkey)` is only the key. The config file `psp-mint.toml` stays in `PSP_DATA_DIR` itself.

**The node is checked.** At startup and before every scan the mint asks the node (`getblockchaininfo`) which chain it is on, and stops if that is not the configured network. `/health` and `/audit` carry `"network"`, and the ESP mint and the wallet check it before they talk to the PSP.

## Settings

Every setting is in `psp-mint.toml` in the data directory (or the file `PSP_CONFIG` names, which must then exist), and each has an environment variable that overrides the file. Strongest first: the environment, the file, the default. The file is TOML in sections:

```
[settle]
base_confirmations = 3
confirmation_tiers = "10000:4,50000:5,100000:6"

[claim]
max_attempts = 2
write_fee = 0

[delivery]
read_fee = 0

[bitcoin]
wallet = "psp"
```

The settings are read when the mint starts, and logged then with the value in use and where it came from (`default`, `file` or `env PSP_...`). `cargo run -- config` prints the same list and exits. An unknown key, a value of the wrong type or a value out of range stops the mint with a list of every problem. `SIGHUP` reads the file again while the mint serves (see "Reloading, restarting and snapshots"). `PSP_DATA_DIR` (default `~/.psp-mint`) is not a setting, because the file lives in it.

The tier is chosen once, when the price is locked, and stored with the payment, so a change does not touch payments already locked. An empty value means no tiers. A payment that is locked, open, landed and unclaimed, not stored on AIR yet or being claimed is never removed. The mint keeps a few dozen bytes of each removed payment: its txid and block time (so a scan can never owe it again), its place in its claim key's count of owed records (so an index is never reused) and its share of the `/audit` totals (so they never shrink); `settle.prune_horizon_days` says how long the first two are kept. | `settle.prune_horizon_days` | `PSP_PRUNE_HORIZON_DAYS` | `210` | days; 0 keeps every marker | reloads live | How long the mint remembers a payment it removed from `settlements.json` (see `settle.retention_days`), counted from the payment's block time. A removed payment's txid, and a claim key's count of removed owed records, are dropped once their payment is older than the cutoff, and a payment with no record whose block time is before the cutoff is ignored by the scan (counted and logged once per pass), so the file is bounded by the payments of the last horizon, the live ones and a fixed-size total. Raising this setting does not bring back a marker that was already dropped. The cost: a payment first seen after the cutoff has passed its block (the scan blind to it for longer than the horizon, or a rescan of very old blocks) is not settled. Where the markers go, the owed index of an old claim key may be reused, which is harmless: a payer keeps the one-time claim key only until its first read plus 30 days. With `settle.retention_days` above 0 it must be at least 2 x `settle.retention_days` + 30 days (the mint refuses to start, or a reload that breaks it changes nothing, and the message names both settings), and at most 10,000. **0 = keep everything**: no marker is ever dropped and the cutoff never moves. | `claim.write_fee` | `PSP_CLAIM_WRITE_FEE` | `0` | PSP units | reloads live | Whole PSP units, 0 or more, with no cap. | `delivery.read_fee` | `PSP_DELIVERY_READ_FEE` | `0` | PSP units | reloads live | Whole PSP units, 0 or more, with no cap. The read cost the PSP prepays for each record a payer must read: the owed record and the answer to the claim. It is taken twice from the units the payment is owed. A payment whose costs (twice this, and `claim.write_fee`) are as much as it buys is **kept** with nothing owed: no owed record is written and `/audit` counts it under `kept`. The owed record and the answer show it as `read_prepaid_units`. Meant to be very small. Fixed for a payment when its price is locked. **`air.enabled` (`PSP_AIR_ENABLED`) is gone.** The AIR listener always runs, because it is the only way a wallet reaches this mint. A config file or an environment that still sets it stops the mint with a message that says so; delete the setting.

**Removed in 0.8.0.** `settle.min_confirmations`, `settle.price_tolerance`, `settle.payment_reconciliation_target`, `settle.reconciliation_window_days`, `reconciliation.fee`, `reconciliation.max_attempts`, `reconciliation.write_fee` and `reconciliation.round_up_from` (and the earlier `settle.underpay_tolerance_bps` and `settle.credit_threshold_bps`) are gone, with their environment variables. A config file or an environment that still sets one stops the mint with a message that names it and says what replaces it (`reconciliation.max_attempts` and `reconciliation.write_fee` are `claim.max_attempts` and `claim.write_fee`); delete the setting. The claim window is not a setting: it is 30 days (`sp_wire::psp::CLAIM_WINDOW_SECS`), counted from the moment the owed record is stored on the AIR server.

**Fees are 0 by default.** `claim.write_fee` and `delivery.read_fee` are fees in PSP units, and nothing is taken unless they are set. A melt, a rollover, a swap and a spend are exact (the amounts in equal the amounts out).

The ranges are checked when the mint starts. They are wide on purpose: they refuse values that cannot work (0 confirmations, a ceiling too small for one note, a base below the lock) and values far outside any sensible use (a 1 GiB body, a 1000-confirmation wait, a day between scans), not values that are merely unusual. `settle.base_confirmations` and every tier must also be at least `settle.lock_confirmations`, so a price is always locked before the owed record is written.

The numbers in the other documents (1 confirmation to lock, 3 to 6 to be owed, the 30-day claim window, 2%, 120 s, 420 s for `/health`) are these defaults.

The price feeds are not settings. The three sources (Coinbase, Bitstamp and Gemini, see [DESIGN.md](DESIGN.md), "Price") and their URLs are fixed in `src/price.rs`, and only those three are allowed. Changing a feed means changing the code.

## Reloading, restarting and snapshots

A running `serve` is changed with signals. Reloading and snapshots do not stop the mint's service for wallets; a restart does, briefly.

| Signal | What it does |
|---|---|
| `SIGHUP` | Reads `psp-mint.toml` and the environment again. Every setting marked **reloads live** applies at once. A setting marked **needs a restart** that the file changes is named in the log, with the old and the new value, and keeps its running value until the mint is restarted; nothing is restarted. A file with any problem changes nothing; the log says what is wrong. |
| `SIGUSR1` | A snapshot of the network's data folder (see "Snapshots"). |
| `SIGTERM`, `SIGINT` | Stop: the requests being answered finish, every store is written and closed, and the process exits with status 0. |

With `systemd`: `systemctl reload psp-mint` (`SIGHUP`) and `systemctl kill -s USR1 --kill-whom=main psp-mint`. With `launchd`: `launchctl kill HUP|USR1 system/<label>`. `spi reload` sends `SIGHUP` and `spi snapshot` sends `SIGUSR1`. The environment is the one the process started with: a variable changed later is not seen, so change the file.

Every setting is one of two kinds, and the Settings table marks each one (`config::SPECS`, field `reload`):

- **Reloads live** (applied on `SIGHUP` with nothing reopened): `server.melt_max_request_bytes`, `server.rollover_max_request_bytes`, `rollover.max_items`, `server.burns_max_request_bytes`, `server.check_state_max_request_bytes`, `bitcoin.rpc_url`, `bitcoin.cookie`, `bitcoin.rpc_timeout_secs`, `scan.interval_secs` (from the next wait), `scan.health_intervals` and `scan.health_grace_secs` (the next `/health` uses them), every `price.*`, every `settle.*` (the retention and the horizon are read at the next expiry check), every `claim.*`, `delivery.read_fee`, `burn.enabled`, `burn.threshold_psp`, `burn.balance_file` and `burn.balance_max_age_secs`. Fees and limits are all here. A request already being answered finishes with the values it started with.
- **Needs a restart**: `server.bind`, `bitcoin.network`, `bitcoin.wallet`, `rotation.activation_hours`, `rotation.period_hours`, `storage.mint_state`, `air.server`, `air.host`, `air.held_reads` and `air.timeout_secs`. Each is read once, when the mint opens its data, because it shapes something that stays open for the life of that opening (the listening socket, the key sets, the AIR connection); [DESIGN.md](DESIGN.md), "Restarting", gives the reason for each. Until the mint is restarted it keeps the value it has and the log says so.

### Restarting (a brief downtime)

A setting that needs a restart, and a new version of psp-mint, take effect when the process is stopped and started again. That is a brief downtime, and it is the only thing besides a decommission that stops the mint. One process holds the mint's data (sled's exclusive lock), so the new process starts only after the old one has stopped. While it is down, a wallet's AIR request waits in its mailbox slot on the AIR server and is answered when the mint is back (the listener resumes from the stored counter `air_mailbox_next`, and a reply is written once); the local API refuses connections, and its callers (the SPI, esp-mint) retry.

With the SPI, `spi restart psp-mint` does it: it says that the AIR service and every mint it runs will be shut down, asks for confirmation, and changes nothing without it. `spi upgrade` does the same for a new version and checks that `/health` reports the version it installed.

The stop takes as long as the slowest thing it waits for: the scan finishes the RPC it is in (`bitcoin.rpc_timeout_secs`, 30 s by default), the AIR listener finishes the slot it is answering, the local API gets 30 s to finish its requests, and the runtime then gets 5 s to drop what is left. The service files give the stop 90 s (see `ops/` in the SPI).

### Snapshots

`SIGUSR1` copies the network's data folder (keys, notes, records, the scan checkpoint, the AIR counter, `revenue/`) to `<data folder>/snapshots/<UTC time>/`. The scan stops after its pass, the AIR listener finishes the request it is answering and stops (a request wallets send meanwhile waits in its mailbox slot), the local API stops accepting and finishes the requests it is answering (30 s at most) while its listening socket stays open, so a connection made now waits in the kernel's queue. Every thread is joined and the mint, its records and the rotation are dropped: sled writes everything and releases its lock when the last handle goes. Then the copy is made, of files nothing has open, and the mint opens its data again. If a task still holds the data after the local API was stopped, the snapshot is refused with a log line and the process exits with status 1 so that the service manager starts it again, because the mint cannot open files that a task of its own still holds.

`snapshots/LATEST` names the newest complete folder and is written last, so whoever reads it never sees one that is half copied; a copy that fails is removed and the mint goes on. **The folder holds the mint's keys** (mode 0700, readable by the mint's account only). The copy is the whole folder, so the pause grows with its size, roughly linearly: the copy and its `fsync`, plus the time sled takes to open the data again. A connection the local API had accepted but whose request it had not read yet is closed when it stops, which no server can avoid; the clients of the local API (the SPI, esp-mint) retry a read on a closed connection, so they get their answer. To start a mint from a snapshot, put the folder's contents at `<base>/<network>/` with the mint stopped.

## The AIR listener

Wallets reach this mint over AIR and only over AIR. The calls are **mint info** (what `/health` reports: `status`, `wire_version`, `network`), the three reads of the mint's keys, **keys**, **keysets** and **rotation**, and the four calls with a body, **rollover**, **check-state**, **spend** and the **purchase claim** (kind 15, see "Claiming a purchase"), each answered with a reply signed by the mint, except that a claim that is not accepted is not answered at all. `serve` always starts the listener (a thread beside the HTTP server), and refuses to start without `air.server` and `air.host`. What is left on HTTP is local to the SPI: `/melt`, `/burns`, `/audit` and `/health` (see "Local HTTP API"), on a loopback address.

- **How it works.** The listener holds reads on the next `air.held_reads` (16) mailbox slots of the mint's DID on the configured AIR server. When a wallet writes a sealed request into one, the listener opens it with the mint's DID key (`mint_did_key.json`, the one that already opens PSP payloads), answers with the JSON body of the request's kind as it is now (for mint info the status and the wire version and network `/health` reports; for keys, keysets and rotation the key list, the keysets and the rotation window), signs the reply with the same key, seals it to the wallet's one-off key and writes it into the reply cell only that wallet and the mint can find. The reply cell is write-once, so the first write wins: a request that reached the mint twice, or two mint processes, give one reply. Any other kind of request is logged and skipped.
- **Rollover and check-state.** The body is the request JSON the route takes (sealed to the mint's DID with the rest of the request, so the notes in it are readable by the mint only), and the reply body is the JSON the route returns. The ceilings are `server.rollover_max_request_bytes`, `server.check_state_max_request_bytes` and `rollover.max_items`. A refusal is a signed reply with status `refused` and a JSON body with `error` and `code` (a keyset code, `note_spent_elsewhere` with `spent`, and so on); over a ceiling the body is the `request_too_large` JSON (`size_bytes`, `limit_bytes`), a body that is not a request is `malformed_request`, and a failure of the mint's own is the signed `unavailable`. **A resent request is not applied twice:** the rollover is stored by request hash before any note is spent, so a retry, a copy in another slot, a crash between answering and writing the counter and a wallet that starts over all get the stored answer. A rollover holds the mint lock while it runs; the listener reads no further slots meanwhile.
- **Spend (kind 14).** A payment in PSP: notes in, change out, an amount `pay` that is the SPI's revenue. The body is `sp_wire::psp::PspSpendRequest` (`input_keysets`, `inputs`, `keyset` for the change, `outputs` for the change, `pay` in PSP units, `memo` of at most 256 bytes); every input's `spend_signature` covers its digest, which names `pay`, the memo, every input's keyset and every output. The inputs must be worth the change plus `pay`, exactly. The reply is the change's blind signatures (`outcomes`, `keys`, the `keyset` and `epoch` that signed them) and `paid`. `pay` is **reissued to the SPI's own ecash-wallet** unless burning is on (`burn.enabled`, off by default): the mint makes the notes itself, saves their plan with the request before anything is burned, and writes them to `revenue/<request hash>.json` in the data folder (a `sp_wire::psp::PspHandover`, mode 0640, in a folder of mode 0750, so the operator in the service's group can read it), where `ecash-wallet receive-psp` takes them in. With `burn.enabled` true the mint reissues only up to `burn.threshold_psp` PSP in all and burns the rest of each `pay`. Only `pay` is ever burned: the PSP the ESP mint burns for an exchange, and the PSP a purchase buys, are not touched. `/audit` counts `pay` in `paid`, split into `burned` and `reissued`. The checks run cheapest first, and any failure burns nothing: shape and sizes (`no_inputs`, `too_many_items`, `memo_too_long`, `missing_keyset`, `nothing_to_pay` for a `pay` of 0, which would be a plain rollover; `not_exact` when the notes are not the change plus `pay`; `duplicate_input`, `duplicate_blind_nonce`), denominations (`bad_denomination`), the keysets (the current or the previous one, as a rollover: `keyset_retired`, `unknown_keyset`), each note's proof and its signature over the digest (`bad_note`, `bad_spend_signature`), and then the spent lists under the mint lock (`note_spent_elsewhere` with `spent`, the index of each note already spent; `note_held` for a note an unfinished request holds). A spend with no change names no change keyset. A resent spend gets the stored answer and burns nothing more, and a spend cut short by a crash is finished by the same request sent again (see DESIGN.md, "The spend"). The ceilings are the rollover's: `server.rollover_max_request_bytes` and `rollover.max_items`. A spend adds no fee and no price; fees stay 0. Nothing here attaches a spend to another request.
- **Junk is skipped.** A slot that does not open, is malformed, is of an unknown kind or names a key that is not one is logged and skipped. Junk changes no state; a valid request costs the mint one short lock.
- **A call the mint cannot answer now** (the mint lock is poisoned, or a rotation step failed) gets a signed reply with status `unavailable` and no body, so the wallet fails at once with the reason instead of waiting out its tries. Mint info is always answered (a poisoned lock is `mint_lock_poisoned`, as in `/health`).
- **What the signed reply gives.** The keys come in a reply signed by the mint's DID key, so nothing between the wallet and the mint, not the AIR server and not a man in the middle, can substitute keys.
- **The counter** (`next`, the lowest slot not finished) is the text file `air_mailbox_next` in the network's data folder (`~/.psp-mint/<network>`), with the rest of the mint's local state, and **not** under `storage.mint_state`: it is only an optimisation. Without it the listener starts at slot 0 and an answered slot finds its reply cell taken and is passed over. It is written by temp file, fsync and rename after each slot is finished, so a crash between answering and writing it repeats a slot, which is harmless. A damaged counter file stops the listener with a message; it is never replaced.
- **If the AIR client gives up** (more than five held reads end within ten seconds, which is what a session the server refused or closed looks like, or a reply could not be written after three tries) the listener logs `AIR listener failed: ...` and the process exits with status 1, because a mint that no wallet can reach is not running. A supervisor restarts it, and the listener resumes from the counter. A restart of the AIR server needs nothing: the client reconnects and its held reads resume.
- **Held reads left behind by a stopped listener are never cleaned up by the AIR server** (upstream item 17); with 16, a handful of restarts costs little.
- **The AIR server** is the one bundled with the SPI, reached over loopback; its name is `air.server` and its host `air.host`. Resolving the server from the mint's DID is upstream item 4; until then both are settings.

## Delivering a purchase

A purchase carries **no notes**. The payer's wallet makes a throwaway key (the **claim key**) for the purchase and pays bitcoin to the mint's address with one data output that holds only that key's DID, 33 bytes, sealed to the mint's DID (113 bytes on the chain). Wire version 4; payloads of version 3 do not decode.

The mint handles a payment in two steps (`settle.rs`):

1. **Lock.** At `settle.lock_confirmations` (1) the BTC/USD price is locked and stored, once. The payload is opened and read. From the locked price come the units the payment is owed (whole units, 10 cents each, rounded **down**), the prepaid costs that come off them, and the **confirmation tier**: the payment's locked USD value picks the confirmations it must reach (`settle.base_confirmations`, or the tier of `settle.confirmation_tiers` it meets or exceeds, 3, 4, 5 or 6 by default), and the tier is stored with the payment. A payment with no readable payload (no single data output, a payload that is not a claim key), or whose prepaid costs are as much as it buys (owed 0 units), is **kept**: no owed record is written, the payer takes the loss, and `/audit` counts it under `kept`. The sub-unit remainder (under 10 cents) is kept too, and `/audit` adds it up as `subunit_kept_cents`.
2. **Owed.** When the payment has the confirmations of its tier, the mint writes the **owed record** to the AIR server (`air.server`, `air.host`) at an address only the claim key's holder and the mint can compute (`sp_wire::air_request::delivery`; cell *n* is `sha256("sp-psp-owed-v0" || PSP DID || claim DID || n)`, where *n* counts the owed records the mint has made for that claim key, from 0, and a record that was removed by retention still counts, until its marker passes the horizon). The record is signed by the mint's DID key and sealed to the claim key. It says what the payment is owed (`due_units`), the txid, the sats paid, and the terms of the one claim: kind 15, the prepaid costs, `window_secs` (the length of the claim window, 2,592,000 seconds), `max_attempts` and what happens on expiry. The record names no end time. The wallet reads cell 0, 1, 2 and so on until one is empty, claims each record once as soon as it has read it, and keeps its claim key until its first read plus `window_secs`. **Nothing is signed yet.**

A payment that has not reached its tier, or that a reorg took out of the chain, is owed nothing and is looked at again by every scan. Once the owed record is made it is not undone: a reorg deeper than the payment's tier, after it, is the mint's loss (the tiers are the depth the mint accepts).

The owed record is stored in the payment's settlement record first and written after every scan until the AIR server has it, with a wait that doubles from 10 seconds to 15 minutes between tries of one record, across restarts, and the same bytes are written at every try. A delivery never blocks or undoes settlement. **Records are written in index order.** In one pass the mint writes only the lowest owed record of each claim key that is not stored yet; index 1 waits until index 0 is on the server, so a wallet that reads cells in order and stops at the first empty one never stops before a record that lands later. A record the mint has given up on (another record is in its cell) does not hold the later ones back. **The claim window starts when the record lands**: in the same write that marks the record stored, the mint sets `landed_at` to its clock and `open_until` to that time plus 30 days (`sp_wire::psp::CLAIM_WINDOW_SECS`, not a setting). An AIR server that is down for a long time costs the payer nothing: the window has not started. A record that has not landed is never expired and cannot be claimed (a claim for it is ignored as an unknown record, and not counted). A copied payload pays the claim key's holder each time: two payments with one payload are two owed records, at index 0 and 1, each claimable once. Never refunded (decided 2026-10-22, ROADMAP.md "Shared items"). See [DESIGN.md](DESIGN.md), "The owed record".

## Claiming a purchase (kind 15)

One AIR request kind turns an owed record into notes, `KIND_PSP_CLAIM` (15). The body is `sp_wire::psp::ClaimRequest`: the `claim_did`, the `record_id` of the owed record, the `keyset` to sign with (it must be the current one), the blinded `outputs`, and a BIP340 `signature` by the claim key over the claim's digest. The digest covers the PSP mint's DID as well as the claim DID, the record id, the keyset and the outputs, so a claim made for one mint cannot be replayed to another. The wallet sends **exactly one claim per owed record**, for exactly `due_units`.

**The checks, in this order** (`claim.rs`): the shape (size, at least one output, a keyset named); the **signature by the claim key, before anything is read or counted**; the owed record it names (the claim DID and the record id; an unknown one, or one not stored on the AIR server yet, is ignored); a claim already accepted (the identical resend gets the stored answer, any other claim for that record is refused); the window (a claim at or after `open_until` is refused, and so is one for a record the expiry pass closed); the keyset (the current one: the previous gets `keyset_not_current`, a retired one `keyset_retired`, an unknown one `unknown_keyset`; none of these is counted); the content (denominations the mint has, no repeated blind nonce, outputs that add up to **exactly** `due_units`, blind nonces never signed before); then the mint signs and stores the answer by the claim's hash.

**No refusal replies.** An accepted claim is answered with `ClaimResponse` (the signatures, the keysets, `issued_units`, and the prepaid costs that were taken); anything else gets no reply at all and the reason is only in the mint's log, with a code: `bad_signature`, `unknown_owed`, `already_claimed`, `claim_expired`, `too_many_attempts`, `in_progress`, `wrong_total`, `unknown_denomination`, `duplicate_blind_nonce`, `blind_nonce_used`, `keyset_not_current`, `keyset_retired`, `unknown_keyset`, `malformed_request`, `request_too_large` and `unavailable`. A claim signed by the right key, for an open record, refused for its content and not a resend of an earlier refused claim is one **counted attempt**; the record accepts `claim.max_attempts` of them. A bad signature, an unknown record (or one not stored on AIR yet), a claim that names a keyset that is not the current one, a claim after the window or after the accepted one, a resend of a refused claim and a failure of the mint are not counted. A wallet that gets no reply after a while sends the identical claim again.

**Crash safety.** The accepted claim is saved on the payment's record, in full, before anything is signed. A crash between that and the stored answer is finished at the next start and at the top of every scan pass (`service::recover`), **without the wallet sending the claim again**; its identical resend then gets the stored answer. A blind nonce the crash had already signed is signed again with the same key, which gives the same signature and is not counted twice. **New work is always signed with the current keyset**, the finish of a recovered claim included: a claim accepted just before a rotation and finished after it is signed by the new set, and the answer names that set. Every keyset has a key for every power of two, 1 to 2^63 (64 keys), so the new set can sign any accepted claim. **The issued total can then overstate, and the bound is exact.** The units the old set had already signed before the rotation stay in its issued total, and the new set counts the whole claim again, so `issued` in `/audit` (summed over the sets) is higher than the units claimed by at most the outputs of the claims that were pending (accepted and not answered) when the mint rotated. Normally that is no claim: a claim is accepted and answered in one step, and `service::recover` finishes any that is not before the keysets rotate. After a crash it is at most one claim (claims are taken one at a time, so a crash leaves one mid-signing). A claim whose answer could not be written also stays pending, with every output signed, for as long as the write keeps failing, and a rotation asked for through the API can come in that time. The mint does not correct `issued` and keeps no counter for it; the claimed units (`claims.claimed.units`) stay exact. A claim accepted before the window closed is finished after it.

**What is claimed.** The units the payment buys at the locked price (rounded down), less twice `delivery.read_fee` and `claim.write_fee`, never below 0. After the window closes unclaimed the mint keeps the bitcoin: `/audit` shows it as `expired`.

**Retention and the horizon.** `settlements.json` is rewritten whole on every change, so it is kept small in two steps, each with a setting where **0 = keep everything**.

*Retention* (`settle.retention_days`, 90 by default; 0, or 30 to 3,650). A payment is removed from the file this long after it finished: claimed (its claimed time), expired (its expired time), kept with nothing owed (its kept time) or abandoned, which is a payment whose owed record could never be written (the time it was given up on). A payment that is locked, open, landed and unclaimed, not stored on AIR yet or being claimed is never removed. What stays of a removed payment is small and does not shrink the books: its txid goes on a list with its block time, so a scan that sees the payment again never owes it twice; its place in its claim key's count of owed records is kept, so the next index for that key is still new; and its share of the `claims` totals in `/audit` is added to a fixed-size running total, so those totals do not go down (an abandoned payment's share stays under `unclaimed`). A claim sent again after its payment was removed gets no reply (an unknown record). With retention 0 nothing is ever removed and no marker is made; the claim windows still close on time, and an expired payment simply stays in the file.

*Horizon* (`settle.prune_horizon_days`, 210 by default; 0, or at least 2 x retention + 30 and at most 10,000). The txid list and the counts would otherwise grow for ever (about 90 bytes for each removed payment and about 150 for each claim key), so they are bounded too. At each prune pass a **cutoff** moves forward to the larger of itself and now less the horizon, and never back. A removed payment's txid is dropped once its block time is before the cutoff, and a claim key's count is dropped once its newest payment is before the cutoff and the file holds no record of that key. A payment with no record whose block time is before the cutoff is ignored by the scan, and the pass says how many. So the file is bounded by the payments of the last horizon, plus the live ones, plus the fixed-size totals. With horizon 0 no marker is dropped and the cutoff never moves; with retention 0 there are no markers to drop (any horizon is accepted, and a marker made earlier stays). Both settings reload live, and a reload into or out of 0 applies at the next prune pass.

What holds, and what it costs:

- **Never owed twice.** A payment is in the file, on the list, or older than the cutoff, and the cutoff only moves forward. Raising the horizon by a reload does not bring a dropped marker back or move the cutoff back.
- **The `/audit` totals never shrink.** They are the payments in the file plus the aggregate of the removed ones, which is never dropped.
- **Reusing an index beyond the horizon is harmless.** A payer keeps the one-time claim key only until its first read plus 30 days, and a count is dropped only when its newest payment is more than the horizon old, which is at least twice the retention plus 30 days.
- **The cost.** A payment first seen after the cutoff has passed its block (the scan blind to it for longer than the horizon, or a rescan of very old blocks) is not settled. The cutoff moves only at the end of a prune pass, so a restart alone does not cause it.

## Local HTTP API

The HTTP API is local to the SPI and the operator; wallets do not use it (they use AIR, above). It is served on `server.bind`, which must be a loopback address. The handlers are this mint's own, over the PSP's own mint in the same process (mint-core's `AppState`: the mint behind one mutex); `/melt` also keeps the memo of each burn (see [DESIGN.md](DESIGN.md), "Burn memos"), and `/burns` is a route of this mint only. The bodies of `/keys`, `/check-state` and `/melt` are sp-wire's (`keys`, `melt`). The scanner and the API share the mint behind one mutex. The scanner locks it once per payment and never while it waits on the exchanges for a price.

| Route | What it does |
|---|---|
| `POST /melt` | Burns notes. Body: `{"inputs": [...], "memo": "..."}`. Every input's spend signature covers the memo, so the burn is bound to it. Returns `{"burned": ...}`. The ESP mint uses this to burn PSP in an exchange, with the memo it computes from the request. The memo is kept for every note the burn spends, and only after every input has been checked: a `400` means nothing was burned and nothing was recorded, and a fault of the store is a `500`. A rollover or a spend that burns a note clears any memo an earlier melt left on it. |
| `POST /burns` | Body: `{"nonces": [...]}`. Returns `{"burns": [{"spent": true, "memo": "..."}, ...]}` in the same order. `memo` is the memo the note was burned under, and is `null` if the note is not spent or was spent with no memo on record. The ESP mint uses this on a retry. See [DESIGN.md](DESIGN.md), "Burn memos". |
| `GET /audit` | `issued`, `redeemed` and `outstanding`, which are **decimal strings** (totals are `u128`; a JSON number cannot hold one past `u64`), `paid` (the PSP units paid to the SPI by spends, kept apart from every other burn such as an exchange's `/melt`; the inputs of a spend are part of `redeemed`), of which `burned` (destroyed) and `reissued` (made again as notes for the SPI's wallet, in `revenue/`; part of `issued`), and `claims`: `claimed` (the notes were signed), `unclaimed` (owed, inside the window), `expired` (the window closed unclaimed, the mint keeps the bitcoin) and `kept` (no readable payload, or nothing left after the prepaid costs), each with `payments`, `sats` (the bitcoin) and `units` (the units owed; 0 for `kept`); the sub-unit amount kept by rounding, `subunit_kept_cents`; the prepaid costs of the claimed payments, `read_prepaid_units` and `write_prepaid_units`; and `refused_attempts` (claims refused for their content, so an operator can answer a support request). `paid`, `burned`, `reissued` and the claims figures are JSON numbers. The claims figures include the payments removed by retention. A payment that is owed is not part of the issued, redeemed and outstanding totals until it is claimed. After a rotation `issued` can be higher than the units claimed, by at most the outputs of the claims that were pending across the rotation (normally none, one after a crash; a claim whose answer could not be written also stays pending); `claims.claimed.units` is exact. See "Claiming a purchase (kind 15)", **Crash safety**. |
| `GET /health` | `200` with `status` `ok` (or `starting`, before the first scan finishes), `503` with `scan_stale` or `mint_lock_poisoned`. The body also has `version` (this build's version, which `spi upgrade` reads after a restart to see that the new build is the one answering) and `wire_version` (an integer: the version of the wire format this mint speaks; a wallet refuses a mint whose number is not its own), `last_scan_unix`, `seconds_since_last_scan` (both null until a scan succeeds) and `stale_after_secs`. A scan counts when the wallet was read and every payment was processed as far as it could go, so a payment waiting on confirmations or a price is not a failure. `scan_stale` means no successful scan for `scan.health_intervals` intervals plus `scan.health_grace_secs` (by default three intervals plus 60 s). |

Gone from HTTP (they are AIR calls now): `GET /keys`, `GET /keysets`, `GET /rotation`, `POST /rollover` and `POST /check-state`. A request for one is a `404`. They are answered by the AIR listener with the same bodies; see "The AIR listener".

`/melt` and `/burns` have a ceiling, 1 MiB by default (`server.*_max_request_bytes` above); so do the two AIR calls with a body, with the same JSON for a refusal. A body over it is refused (`413` over HTTP) before it is parsed, so nothing is burned. A body that gives its `Content-Length` is refused without being read; one sent without it is read only up to the ceiling. The reply is JSON, with `error` like every other error here, plus `code` (`request_too_large`), `size_bytes` (the declared size, or `null`) and `limit_bytes`, as the ESP mint's `413` has:

```
{"error":"the request is 1048577 bytes, and this route accepts at most 1048576 bytes. Nothing was parsed or burned","code":"request_too_large","size_bytes":1048577,"limit_bytes":1048576}
```

Not mounted, on purpose:

- **`/admin/issue`.** The PSP issues only from confirmed BTC payments. There is no unilateral issuance.
- **`/swap`.** PSP to FSP is out of scope. The plain PSP swap that settles a wallet-to-wallet hand-over is the rollover, over AIR.

`serve` also exits (status 1, with a message on stderr) if the scan thread panics or a thread panics while holding the mint, since either leaves a process that answers but is broken. A supervisor should restart it.

There is no authentication and no TLS, and `/health` is open like the rest. A note authorizes its own spend, so a caller can only burn notes they hold. The bind must be a loopback address (the settings refuse any other), so the API can be reached only from this machine; do not put a proxy in front of it.

## Wire version

The request and response types come from [`sp-wire`](../sp-wire/README.md), and `GET /health` returns `wire_version`. A wallet refuses a mint whose number is not its own. Details in [DESIGN.md](DESIGN.md), "Wire format and versions".

| `docs.rs` | This README against the program: its commands are the ones `--help` prints and its settings table is the table the program reads. |
| `limits.rs` | Body ceilings on `/melt`, `/burns` and over AIR: refused before parsing, nothing burned. |
| `network_http.rs` | `/health` and `/audit` carry the network. |
| `rotation.rs` | Key rotation and rollover over AIR: previous notes kept for one period, a rollover with a spent input burning none, one interrupted after the burn and finished by the retry, a melt mixing both sets, resumed rollovers after a retirement. |
| `spend.rs` | A spend with change over AIR (kind 14). |

What the tests do not do: nothing here starts bitcoind. `cli.rs` cannot run a scan that finds payments, or `serve` past its start-up checks; `cycle.rs` covers the pass through the library with a stand-in node. The end-to-end run with a Bitcoin Core regtest node is [REGTEST.md](REGTEST.md). The tests that use AIR take turns on one local `air_server` (port 5702 must be free).
